# Последовательные ECS-системы с параллельной обработкой пакетов

Принято пользователем 2026-10-31. Системы выполняют обработку строго последовательно: все пакеты SystemA завершаются до начала обработки SystemB. Внутри каждой системы независимые пакеты распределяются между рабочими потоками. После завершения логики и подготовки данных объектов записываются существующие GPU-проходы с ExecuteIndirect; отдельная параллельная запись draw-команд объектов исключена последующим решением [ADR-0003](0003-indirect-rendering-parallel-object-preparation.md).

Это сохраняет заданный порядок изменения общих компонентов: существующие системы Movement, CircleMovement и SplineFollow записывают Transform, а LookAtTarget читает положение других сущностей. Альтернатива с одновременным выполнением разных систем и автоматическим графом конфликтов не входит в выбранную модель.

Пользовательский ориентир API — Unity Jobs. Первая версия ограничена наследуемыми Job::Execute() и ParallelJob::Execute(index): первый обрабатывает данные системы последовательно, второй — параллельными пакетами. Внутренний планировщик — enkiTS. ParallelJob::Schedule возвращает JobHandle; пользователь выбрал возможность связывать системы зависимостями через handles, чтобы сохранять порядок обработки без обязательного ожидания вызывающего потока между параллельными этапами. Complete остаётся точкой завершения CPU-работы.

Сохраняем собственный ECS. Проверочная нагрузка — движение существующих бутылок, столов и стульев Bistro без добавления копий. Объекты работ и используемые ими данные живут до завершения; активный объект работы нельзя изменять или повторно планировать. Порядок и зависимости явно задаются приложением в Tick/Update, как описано в [ADR-0002](0002-application-owned-update-order.md).
