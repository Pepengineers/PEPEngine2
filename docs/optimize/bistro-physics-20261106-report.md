# Bistro: стоимость физики и упрощение коллайдеров

6 ноября 2026. Исходная физика — `5a088ee`, рабочая ветка `codex/debug-frame-hotspots`.
Существовавшие незакоммиченные изменения рендера принадлежат другой задаче.
Машина измерений: AMD Ryzen 7 5800HS, 8 физических / 16 логических ядер.

## Результат

В трёх последовательных парах Debug x64 средняя стоимость fixed tick уменьшилась
с **18,45 до 6,75 мс** (медианы средних по запускам, **−63,4%, 2,73 раза**).
Частота 60 Гц, четыре collision substeps, CCD, solver, число объектов и импульсы
не изменялись. Это результат физического шага без GPU и без рендера, не FPS приложения.

| Пара | Исходная версия, мс/tick | Боксы, мс/tick |
|---|---:|---:|
| 1 | 18,6975 | 6,6896 |
| 2 | 18,4455 | 6,7475 |
| 3 | 18,2194 | 6,8737 |

Все шесть прогонов: настоящая геометрия Bistro, 379 динамических тел, два статических
mesh, 16 потоков, seed 12345, три полные волны, 1827 fixed ticks. Порядок:
candidate/baseline, baseline/candidate, candidate/baseline. Сборки и другие наши
нагрузочные тесты не пересекались с этими шестью прогонами. Частоты CPU не фиксировались.
Даже худшая пара выигрывает больше 62%; порог принятия — 2%.
Медиана p95 по прогонам: 32,80 → 14,97 мс.

Первоначальные `Baseline-t16-s1` и `baseline-clean` исключены: они пересекались
со сборкой диагностических executable. Проба только с бутылками дала 17,20 мс/tick,
но отдельная серия подтверждения для неё не выполнялась; её выигрыш отдельно не заявляется.

## Что изменено

- Бутылка получает один ориентированный box по вершинам всех её material sections.
  Сохраняются исходное положение и наклон, включая бутылки в холодильнике.
- Каждый convex hull мебели заменяется ориентированным box. Разбиение мебели на
  части сохраняется: столешница и ножки не превращаются в сплошной габаритный объём.
  Уже распознанные примитивы сохраняются. Минимальная полная толщина box — 1 см.
- Динамика: **2022 convex + 6 primitive parts → 0 convex + 1083 primitive parts**.
  Уменьшены число частей и стоимость геометрии при поиске контактов.
- Повторные экземпляры продолжают использовать существующие shared geometry и
  кэш Jolt shapes. Общий точный baker и его meshopt/V-HACD тесты не менялись.
- `BistroPhysicsTests` выводит среднее и p95 времени непосредственно `PhysicsModule::Step`.
  Импорт, baking, проверка результатов, импульсы волн и ECS sync в эту метрику не входят.

OBB — намеренная грубая аппроксимация. Она заполняет небольшие выемки отдельных
частей и меняет автоматически вычисляемые массу/инерцию; физические траектории
не обязаны совпадать с исходными. Это разрешённый пользователем компромисс.

## Распараллеливание и лишняя работа

Jolt использует общий enkiTS scheduler, отдельный пул потоков не создаётся.
`GetMaxConcurrency()` включает главный поток, который исполняет готовые задачи
через Jolt barrier. Barrier и enki-обёртка могут попытаться взять один job,
но CAS внутри `JPH::Job::Execute` запускает его функцию только один раз.
`Drain()` завершает ещё живые enki-обёртки; удаление ожидания нарушило бы их lifetime.
Последовательность pre → physics → post необходима для зависимостей состояния.

Отдельный sweep окончательного executable, по одному прогону на конфигурацию
(те же 379 тел / три волны / 1827 ticks):

| Потоки | Среднее, мс/tick | p95, мс |
|---|---:|---:|
| 1 | 23,6764 | 56,6348 |
| 4 | 7,9941 | 19,7614 |
| 8 | 6,4166 | 15,8386 |
| 16 | 6,6883 | 14,5846 |

Проверяемые показатели волн, пиковая скорость и число вышедших из геометрии тел
совпали; побитовое сравнение всех траекторий этим sweep не выполняется.
На 16 потоках шаг в 3,54 раза быстрее однопоточного. Один прогон не обосновывает
жёсткий лимит 8 потоков: сцена и конкурирующая работа общего scheduler могут меняться.
Отдельная holdout-пара с четырьмя потоками: 22,9986 → 7,9941 мс/tick (−65,2%);
это одна пара, не дополнительная тройная серия.

Есть `new/delete` для каждого job и повторное чтение поз спящих тел, но они не
объясняют основной найденный расход. Пропуск всех sleeping bodies без учёта перехода
в сон потерял бы последнюю позу. Пул jobs и дополнительный кэш поз не добавлялись.

Существующий профиль `Build/DebugNext-20261106/jolt-summary.json` показывает
compound/mesh/convex contact generation и solver как крупные затраты; его вложенные
CPU scopes нельзя суммировать как независимое wall time. Новые A/B измерения выше
подтверждают пользу упрощения динамики. Новый детальный профиль Jolt после изменения
не снимался.

## Почему архитектура не заменена одним набором габаритных коробок

Статика уже упрощена до 1 490 198 треугольников. Узлы архитектуры имеют имена вида
`paris_building_01_interior_N`; `Wall` в названиях встречается также у ламп.
Габаритный box такого узла может закрыть дверной проём или внутреннее пространство.
Одна лишь планарность и сходство суммарной площади треугольников не доказывают
отсутствие отверстий: перекрывающиеся поверхности могут компенсировать их площадь.

Безопасный следующий шаг для статики — выделять отдельные замкнутые solid-компоненты
и проверять box-fit; для открытых стен проверять границы и отверстия планарных
патчей. Неподходящие поверхности должны оставаться mesh. В этой итерации крупный
выигрыш получен без изменения архитектурных проходов и опорных поверхностей.

## Альтернативы

Для стандартных 379 объектов замена Jolt не обоснована: измеренное упрощение уже
существенно снизило стоимость при прежних настройках качества. При 6064 телах
стоимость остаётся выше бюджета 60 Гц даже в Release; для этой нагрузки отдельное
сравнение с GPU backend имеет смысл после исправления containment/размещения копий.

- **PhysX CPU:** возможен как native C++ backend; преимущество над текущим Jolt
  можно установить только одинаковым benchmark геометрии, количества тел и качества.
- **PhysX GPU:** ускоряет broadphase, contact generation и solver через CUDA;
  требует совместимую NVIDIA GPU. Это кандидат для отдельного эксперимента с тысячами
  активных объектов, учитывая CPU↔GPU обмен и конкуренцию с DX12 рендером.
  [Официальная документация PhysX 5.7](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/GPURigidBodies.html).
- **Direct GPU API PhysX:** требует изменения нынешней CPU-синхронизации поз/скоростей
  с ECS; это не переключатель существующего backend.
  [Direct GPU API](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/DirectGPUAPI.html).
- **Unity Physics / DOTS:** пакет для поддерживаемой версии Unity, а не готовая
  замена native C++ backend PEPEngine2.
  [Unity Physics overview](https://docs.unity3d.com/Packages/com.unity.physics@1.3/manual/index.html).

Новые зависимости не добавлялись; альтернативные движки не интегрировались и не измерялись.

## Проверки и границы результата

Штатные сборки `App` и `BistroPhysicsTests` в Debug/Release прошли.
В sandbox MSBuild зависал после компиляции; окончательные успешные сборки
выполнены вне sandbox с `/m:1 /nr:false`. Существующие предупреждения
C4267 в renderer и LNK4099 об отсутствующих PDB внешних библиотек остаются.

`BistroPhysicsTests --unit-only 4` прошёл в обеих конфигурациях: перенос/поворот
и охват вершин бутылки, некорректный вход, минимальная толщина, опорные ножки и
столешница, свободное пространство под столом. Общий `PhysicsTests` в Debug
прошёл: 1000 сталкивающихся тел, 180 ticks, 1/4 потока; nested fan-out/fan-in
наблюдает все четыре execution threads и ровно одно исполнение каждой задачи.

Три paired прогона прошли без Jolt assertions, потери тел, нечисловых поз,
расхождения физического/render pivot и нарушения импульсов 500/700 см/с.
В исходной версии два объекта опустились ниже −1000 см, в варианте с боксами — ноль.
Это не доказательство полной герметичности сцены: один пересекающий статику chord
по-прежнему диагностируется (сам по себе chord не доказывает tunneling).

Дополнительные законченные прогоны финальной версии:

|---|---|---|---|
| Release, 16 потоков | 379 тел, 3 волны / 1827 ticks | 3,526 / 6,111 | Все assertions теста прошли, ниже сцены 0 тел |
| Debug, 16 потоков | 379 тел, 10 волн / 4747 ticks | 6,420 / 10,845 | Все assertions теста прошли, ниже сцены 2 тела |

Holdout при scale 16, одна последовательная Debug-пара: исходная версия
**154,955 → 51,758 мс/tick (−66,6%)**, p95 277,671 → 77,604 мс.
Исходная версия уже теряла 381 дополнительное/исходное тело ниже сцены; кандидат —
394. Это ухудшение данного диагностического счётчика на 13 тел, а не улучшение
containment. Число chord-кандидатов снизилось 428 → 24, но этот счётчик сам по себе
не является доказательством исправления tunneling. Release baseline для scale 16
не измерялся, поэтому его ускорение относительно Release не заявляется.

**Containment не исправлен.** Тест диагностирует выход ниже −1000 см, но не считает
его автоматически ошибкой интеграции. Поэтому exit 0 в последней таблице не означает,
что удержание тел в Bistro прошло приёмку. При scale 16 сохраняется большой расход
на физику и проблема выхода дополнительных копий через/за моделированную геометрию;
60 Гц симуляции при scale 16 не достигнуты ни в Debug, ни в Release. Длительный прогон исходной
версии на 10 волн не выполнялся; сравнение числа выходов для этого случая отсутствует.

Нет нового end-to-end FPS/physics-debt сравнения обычного App. Рост скорости одного
тика не доказывает, что приложение теперь всегда успевает симулировать реальное время:
на это влияют остальные стадии кадра и существующий лимит времени catch-up.
Финальный обычный `App` Debug успешно загрузился и отработал 120 кадров (exit 0,
`app-smoke.json`, particle scale 1 / budget 250000). В этом одиночном smoke среднее
время кадра 89,23 мс; это не изолированный A/B результат физики и не доказательство
ускорения всего приложения. Длительный realtime soak, GPU scale 16 и другой CPU/GPU
не проверялись.

Остановлено после подтверждённого выигрыша двух вариантов геометрии и проверок
потоков/нагрузки; новые scheduler-структуры и новый physics backend не вводились.
