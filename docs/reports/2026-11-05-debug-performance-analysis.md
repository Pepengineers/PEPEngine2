Ryzen 7 5800HS, RTX 3060 Laptop 6 GiB, NVIDIA 617.42. Анализ обычного
Debug x64 App, после оптимизации Jolt и collision baking. Продуктовый код
в рамках анализа не изменён.

**Версия измерений:** исходный App.exe имел время сборки 22:12 МСК. Во время

- Отдельный диагностический App построен из копий App.cpp, RenderModule.cpp,

  scopes и чтение существующего GPU timestamp timer. Исходники и обычный
  App.exe не заменялись; временный executable запускался из того же каталога,
  с тем же runtime INI и DLL. Во время этого прогона сборок не запускалось.
- Диагностический прогон: 61 кадр, **1635,21 мс/кадр** по штатному benchmark,
  exit 0. Для разбивки ниже исключены кадры 0–10; анализируются 50 кадров
  11–60. Накладные расходы instrumentation входят в CPU timings.
- Это один ракурс и короткий стартовый сценарий. GPU time — интервал между
  timestamps, а не сумма занятости отдельных блоков GPU. CPU scopes вложены;
  складывать все строки таблицы нельзя. CPU и GPU также могут перекрываться.
- На машине есть другая занятая видеопамять: без App `nvidia-smi` показывал
  около 3,6 GiB, с App — примерно 5,9 GiB. Бюджеты WDDM, evictions и paging
  отдельно этим счётчиком не измеряются. Клоки/температура не фиксировались.
- Во время работы появились посторонние изменения в физике и её тестах.
  Они сохранены; этот отчёт не является проверкой этих изменений.
  Во время позднего Nsight-запуска вне sandbox обнаружены два параллельных
  BistroPhysicsTests (стартовали в 22:30 и 22:33 МСК, после двух CPU-прогонов).
  Этот захват нельзя называть изолированным системным benchmark.

## Приоритет 1: устранить повторное создание SSR-контекста

Код образует цикл, способный удерживать Debug в медленном состоянии:

1. `RenderModule::OnUpdate` при каждом `DeltaTime > 0.25` выставляет
   `RequestHistoryReset`.
2. `GPUDataUpdateSystem` превращает этот запрос в новую `HistoryRevision`.
3. `GDX12SSSRPass::Execute` при изменении revision вызывает `CreateContext`.
4. `CreateContext` уничтожает прежний контекст, ожидает GPU queue через Flush
   и вызывает `ffxSssrContextCreate`, заново создавая ресурсы/SDK state.
5. Следующий кадр снова длиннее 250 мс.

1133 мс в строке SSR — CPU wall time всего Execute, **не измеренное время
SSR-шейдеров на GPU**. В него входят ожидание и создание контекста.

Предложение: разделить сброс temporal history и необходимость пересоздания
SDK context. Повторяющиеся медленные кадры не должны безусловно переинициализировать
SSR. Пауза/возобновление должны давать отдельное событие discontinuity;
camera cut, resize, смена ресурсов/сцены должны сохранять корректный reset.
Если используемая версия SDK не умеет дешёвый history reset, отдельно исследовать
повторное использование pipelines/backend allocations и точечный reset denoiser.
Ожидание перед фактическим уничтожением GPU resources должно оставаться корректным.

### Контрольный эксперимент

В следующую временную сборку добавлены отдельные scopes создания/уничтожения SSR
и возможность через переменную среды пропустить **только** условие
`DeltaTime > 0.25` в OnUpdate. Это диагностическое изменение, не готовое исправление.
Camera/resize/resource resets не отключались; качество не менялось.
Прогон также завершился с exit 0, 61 кадр, без одновременной сборки.

| Метрика, кадры 11–60 | Исходный диагностический App | Без повторного dt reset |
|---|---:|---:|
| Update + Render, среднее, мс | 1503,82 | **810,22** |
| SSR Execute, CPU wall, мс | 1133,31 | **0,412** |
| Graph Execute целиком, мс | 1290,12 | 160,11 |
| GPU timestamp interval, мс | 816,65 | **801,88** |
| CPU Present, мс | 0,41 | 404,95 |

В изменённом прогоне SSR context создавался только на кадрах 0 и 1; на 11–60
пересозданий нет. Штатный benchmark всех 60 кадров дал 965,49 мс против 1635,21 мс;
это окно включает дорогой начальный прогрев. По отдельным прогретым scopes
ускорение Update + Render — около 1,86 раза. Ожидание GPU переместилось в Present;
удалить эти 405 мс отдельной оптимизацией Present из результата не следует.

Замеры поддерживают причинную связь repeated reset → context churn → CPU stall.
Они также показывают, что это **не единственная причина** низкого FPS: даже при
устранении churn в этом нагруженном прогоне GPU-интервал остаётся около 802 мс.
В последующем Nsight-прогоне ситуация изменилась; переносить 802 мс на обычный
запуск нельзя. Нельзя обещать 60 FPS от
одного исправления SSR. Это одиночная пара прогонов с разными временными
instrumentation builds, не статистический benchmark всего приложения.

Артефакты: `suppress-dt-reset.json`, `suppress-dt-reset-stages.csv`,
`suppress-dt-reset-stages.summary.json`. Внутри каталога анализа находятся
`prepare.py`, `build.py`, `summarize.py`; анализ не перезаписывал обычный
executable или INI. Более позднее внешнее обновление executable отмечено выше.

### Качество и границы интерпретации

- Nsight сообщил dropped periodic sampling data. Percent-of-peak counters
  используются только как вспомогательные сигналы, не точная атрибуция причины.
- Native analyzer отверг новый формат WRPV v11 (поддерживает v10). Использован
  экспорт самого Nsight и существующий Python parser. Nsight назвал bundle
  `BASE_UNLOCKED`; его копия `BASE` позволила прочитать экспорт старому wrapper.
- Проверка исходного TSV выявила невозможное значение: один Local shadow draw
  в третьем кадре — 797,322 мс при целом кадре 393,889 мс. **Третий кадр целиком
  исключён из разбивки.** Автоматический вывод «local shadows = 73,1% GPU»
  основан на этом выбросе и отвергнут. Raw export сохранён без правок.
- Два оставшихся кадра — лишь ограниченная иллюстрация распределения работы,
  не стабильная performance-статистика и не результат A/B-оптимизации.
  Полнота всех timestamp buckets отдельно не подтверждена.
- В этом запуске Nsight сообщил VRAM committed 3596 MiB при бюджете 5226 MiB,
  demoted 0 MiB. Это **не подтверждает paging** в данном захвате и не объясняет
  прежние интервалы 800 мс. Состояние памяти/системы между запусками менялось.

На двух оставшихся кадрах elapsed frame intervals — **371,902 и 388,732 мс**.
Сумма корневых GPU-маркеров — примерно **88,94 мс/кадр**. Это согласуется с
низкой graphics-engine activity в собранных counters (~24% всего захвата,
с оговоркой dropped samples). Есть существенные интервалы без GPU-работы;
это поддерживает приоритет CPU preparation/recording, а не универсальный
вывод «GPU требует 800 мс на обычный кадр».

| GPU-маркеры, среднее двух кадров | мс/кадр |
|---|---:|
| Geometry view mesh batches, сумма | **47,43** |
| в том числе Local shadow draw, 222 markers/кадр | 15,42 |
| Bistro grass expansion | 6,46 |
| Particles | 6,39 |
| SSR + denoiser + specular resolve | **5,98** |
| Fluid surface | 4,96 |

Таблица содержит вложенную строку local shadows; её нельзя второй раз прибавлять
к geometry batches. 222 — количество marker instances, не число raw draw calls.
GPU-время SSR около 6 мс не противоречит большому CPU-времени того же этапа.
В кадрах 11–20 этого запуска счётчик SSR context creation срабатывал каждый кадр,
и каждый раз наблюдалось изменение HistoryRevision; медиана CPU CreateContext —
34,47 мс. Его цена сильно зависит от условий запуска, но сам churn воспроизводится.

GPU-кандидаты после исправления CPU-пути: точнее отбирать geometry для каждого
shadow view, уменьшать повторные cull/draw/grass expansion для невлияющих patches,
измерить бюджет обновления динамических local shadows. Static shadow cache уже
есть; добавлять ещё один без измерения нельзя. Для травы нельзя подменять light/probe
frustum главным camera frustum: это удалит нужные off-camera casters.
Снижение shadow resolution, числа источников с тенями и particle budget — отдельные
варианты с потерей качества; их выигрыш здесь не измерялся.

Артефакт проверки и безопасной разбивки: `gpu-validated-summary.json`,
программа `validate_gpu.py`. Она проверяет превышение duration отдельного маркера
над frame interval и исключает соответствующий frame, не редактируя capture.

## Приоритет 2: сократить CPU-работу render graph и grass bindings

Граф содержит **4620** исполняемых узлов и не отсекает ни одного. В
`BistroRenderPipeline::AddGeometry` для каждого view slot и каждого grass patch
создаются expansion и draw nodes, плюс mesh node на view. Проверки активности
выполняются внутри узлов после входа в общий executor.

Сам общий executor стоит около 85 мс, отдельно от Execute passes.
В `GDX12RenderGraph::Execute` для каждого узла создаются buffer-access vectors,
заполняется диагностический LastBuffers, сканируются graph resources.
`GDX12GrassRenderer::DrawAccesses` каждый раз перечисляет constants **всех**
подготовленных outputs, а `FindOutput` линейно ищет view/patch. Это конкретные
кандидаты для уменьшения повторной работы; индивидуальный вклад каждого пока
не измерен.

Предложения по возрастанию объёма изменения:

- Сохранять готовые buffer access lists на frame/view, переиспользовать storage.
- Передавать constants конкретного view/patch, а не всех outputs, где контракт
  зависимостей действительно допускает это. Сохранить зависимости общего arena.
- Искать prepared output по сохранённому индексу/ключу вместо повторного обхода.
- Компилировать точки начала lifetime ресурсов в списки для соответствующих nodes.
- Укрупнить исполнение geometry jobs и рано пропускать неактивные view slots;
  сохранять порядок expand → consume перед повторным использованием arena.
- Рассмотреть единый per-frame constants buffer вместо отдельного upload
  allocation на каждую подготовленную пару view/patch.

Для Debug можно отдельно измерить `/O2` с символами для подтверждённых hot TUs,
сохранив Debug CRT, ABI и assertions. Это ускоряет рабочую отладочную конфигурацию,
но не заменяет устранение повторной работы и затрудняет пошаговую отладку этих TUs.

## Приоритет 3: подготовка сцены

Snapshot стоит около 56 мс. `CollectReflectionScene` каждый кадр проходит mesh
instances, собирает primitive revisions, hashes и caster bounds. Предложение —
кэшировать неизменные static mesh данные по уже существующим revision/dirty
контрактам; динамические transforms и visibility обновлять отдельно.
Нужно проверить смену материалов, удаление entities, world replacement и
off-camera shadow/probe contributors. Измеренного выигрыша от такого изменения нет.

## Физика и загрузка

Jolt уже использует оптимизированную Debug-библиотеку. Около 26 мс на physics
update — существенная стоимость, но она не объясняет секунду в SSR.
Изменение collision substeps, CCD или геометрии не является первым действием
по этому профилю. Уже введённый wall-time budget catch-up сохраняет backlog:
FPS не доказывает, что симуляция догоняет реальное время.

Первый диагностический кадр содержал примерно 30,3 с в PrepareSkeletalMeshes;
это отдельная проблема старта. В предыдущих native samples путь включал
AllocateSkinnedVertices → ResizeVertexBuffer → GPU Flush. Предложение — заранее
посчитать суммарную ёмкость skinned geometry и резервировать её одной операцией,
затем отдельно измерить startup. Полный вклад аллокаций против ожидания GPU
в этих 30,3 с не разделён.

Не выполнены визуальная проверка temporal history после предлагаемых изменений,
длительный soak, обход сцены, scale 16, другие CPU/GPU и проверка новых посторонних
правок физики. Предложения не внесены в продуктовый код.
