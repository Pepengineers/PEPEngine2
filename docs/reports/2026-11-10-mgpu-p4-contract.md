## Как соединить P2b и P3b

- Runtime владеет устройствами, `PlanExecutor`, transport banks и границами submissions. Pipeline владеет выбором проходов, полными declarations и содержимым immutable inputs. CPU jobs могут готовить данные. Native queue, executor и transport calls выполняются одним сериализованным владельцем. P1 `AdapterId` и `QueueId` идентифицируют живые экземпляры. Выбор устройства проверяет физический DXGI LUID, исключает software/primary из secondary candidates и проверяет очереди, shared fences и конкретный payload layout перед принятием маршрута.
- P4 создаёт по одной COPY queue на участвующий адаптер. P1 `crossAdapterFence=true` задаётся при создании queue, чей point пересечёт адаптеры. P4 передаёт эти же очереди в P2b native bindings и P3b transport. Queue outlives executor и transport. P3b владеет bank, layout и slot reservations. P2b владеет `ExecuteCommandLists`, `Wait` и `SignalCompletion` для всех batches строгой цепочки, включая export/import. FIFO проверяется по реальным `QueueId` общих lanes. Это решение заменяет исходный черновик с отдельными transport COPY queues.
- Strict fixture — **один placed plan** с двумя направленными передачами. Primary DIRECT producer → COPY A export → COPY B import → secondary COMPUTE → COPY B export → COPY A import → primary DIRECT consumer/readback. Обе Exact reservations и source slots готовы до записи. P2b получает все device-local views и alias `AllocationId`, исходные и выходные версии, declared COPY_SOURCE/COPY_DEST и batch edges. Import пишет локальную версию, которую затем читает Compute/DIRECT. `ExactInputBinding` предназначен для уже отправленного внешнего input. Внутри этого плана версия создаётся import batch и связывается символическим edge. Фикстура проверяет sequence/epoch/checksum и несколько кадров в полёте.
- P3b выделяет `RecordExportCopies` / `RecordImportCopies` над заранее проверенными bindings и footprint ranges. `RecordPlacedCommands` получает зарезервированные views через `BoundResources`. Copy-only функции добавляют `Copy*` команды на переданный list. Preflight проверяет совпадение native views со slot/alias registrations. P2b обеспечивает declared states и COMMON handoff. Внутри recorder отсутствуют queue submits, `Wait`, `Signal`, `BeginExport`, `BeginImport`, изменение credits и descriptor rebinding. Все lists записываются и закрываются до первого submit.
- Для Latest producer/export также может быть placed invocation. Import остаётся отдельным eligible subgraph с одним COPY batch. `Poll` сначала подтверждает export completion и admission выбирает local credit. Минимальная реализация может вызвать существующий transport `SubmitImport` как эту отдельную стадию на **той же injected COPY queue** под тем же сериализованным owner. Это происходит после completed export, вне graph recording. Receipt вносится в общую модель version/readiness. Кадр выбирает совместимый completed local snapshot или local fallback и никогда не ждёт текущий optional import. Присоединение Latest import к P2b в будущем требует явного binding completed shared export, поскольку текущий `ExactInputBinding` ждёт local import-ready.
- В background fixture независимые `ProducerInvocationId` и `FrameSubmissionId`. Runtime обслуживает `Poll`/retirement и admission по свободным credits. Pipeline передаёт snapshot после завершения подготовки World/ECS inputs. Producer получает собственный ограниченный пул constants/uploads/descriptors и время симуляции с pause/time scale. Отставание записываем отдельно от cadence и optional drop. Прогресс primary сохраняется при занятости unrelated secondary slots.
- Present ждёт только outputs и lifetime, используемые текущим кадром. Primary UI, frame generation и swapchain остаются на primary DIRECT. Финальный primary point защищает primary frame slot и транзитивные зависимости этого кадра. Background owners уходят через свои receipts, даже если последующие frames выбрали тот же snapshot. Exact и Latest могут иметь несколько GPU readers с разными timelines.

### Exact transaction и фактические receipts

1. P3a `TryReserve(ExactVersion)` уже возвращает shared+local indices без `CompletionPoint`. P3b сохраняет source, physical slot handles и bank owner. До `Execute` проверяем доступные reader credits для всех объявленных readers. Под внешней сериализацией capacity можно учесть по configured reader credits, `GetUsage().Readers` и числу запланированных acquisitions. Достаточность ID и конкретную проверку admission согласовать по принятому P3b API. Нужный узкий query для credits допустим, если текущая модель не позволяет дать гарантию. Exact pin остаётся до успешной установки всех readers.
2. P2b удерживает owners через `ViewBinding` и `KeepAlive`. Один вызов `Execute` проверяет зависимости, состояния, binding и FIFO, записывает все lists и отправляет batches. Только executor разрешает plan edges в issued `CompletionPoint`. `Receipt.Batches[PlannedBatchId]` становится источником points для transaction commit. `Poll`, `SelectLatest`, `Reset`, `Cancel`, `TryReconfigure` и посторонние submits не вклиниваются между admission, `Execute` и commit.
3. После полного успешного receipt для каждой передачи вызываем P3a в существующем порядке `BindProducer` → `BeginExport` → `BindExport` → `BeginImport` → `BindImport`. Для Exact `BeginImport` использует заранее закреплённый local slot и уже выданный export point. Эти операции меняют учёт P3a, а native copy уже записан в receipt. Для каждого запланированного reader вызываем `AcquireReader` на imported slot и `BindReader` с point его последнего читающего batch. Затем вызываем `ReleaseExact`. Source reuse остаётся привязан к source-copy completion. Роли export-ready/source-complete и import-ready/shared-release различны. Если обе роли покрывает один batch, они используют один выданный point этого batch. P3a `Follows` допускает равное значение на одном timeline. Дополнительный Signal нужен только при разных фактических границах.
4. Deferred/preflight/recording failure с доказанным **нулём отправленных команд** разрешает повтор с тем же reservation ticket или явную отмену ещё не отправленной reservation. `TryReserve` уже продвинул invocation counter, поэтому после отмены тот же ID не резервируется повторно. После начала native submission даже сбой `Signal` может оставить работающий list без point. Partial/unknown outcome или отказ binding после успешного submit переводит transaction и bank в quarantine. Сохраняем slots, source, descriptors, allocators, queues и известные receipts, прекращаем новые admissions и publication из этого bank. Запрещены `Cancel`/`CancelReader` как unsubmitted, reuse и reconfigure до доказанного drain. При device removal используем terminal teardown. `PlanExecutor` должен различать proven no-submit и potentially submitted, либо P4 трактует неясный failure как potentially submitted.

Перед реализацией сверить с владельцами injection constructor, copy-only signatures и outcome contract. P3a порядок `Begin*` сохраняется. Обычные внешние readers по-прежнему используют только issued local import-ready и сильного owner bank/slot в `ExactInputBinding`.

## Миграция production графа

Пример разреза для A1. `CommonRenderPasses::BindAmbientOcclusion` сейчас связывает `Depth.GetOutput(2)` и normals из `Depth` или `Opaque`. В обоих `LinkInputs` `Lighting` читает `AO.GetOutput(0)`. При MGPU-off этот граф исполняется через текущий `Execute`. При active A1 цепочка идёт от primary depth/normals через primary pack/downsample, P3b A→B, placed secondary AO и P3b B→A к primary resolve/upsample и lighting. Pack создаёт совместимые typed/linear payloads из primary depth/normals. Полноразмерная visibility сохраняет контракт lighting.

Путь поэтапной миграции — legacy участки primary графа и полностью declared placed участки в **одном внешнем плане зависимостей**. Producer/consumer edges определяют разрез legacy `_order`. Для early AO первый участок завершается после depth/normal producers. Для late — после `Opaque`. Независимые primary shadow/GBuffer passes можно планировать между export и consumer, если зависимости это позволяют. Tail начинает читать visibility после её реального local readiness. Plan содержит boundary accesses, версии, реальные queue bindings и edges через transport COPY. После раскрытия placement проверяются FIFO и credits. Wait ставит исполнитель плана по issued receipt в точной границе, включая COPY→DIRECT/COMPUTE. Pipeline связывает inputs/outputs. Внешние циклы и ожидания на ещё не выпущенные signals отклоняются до зависимого submit.

Legacy участок сохраняет существующий `Execute` state/hazard tracking внутри primary domain, включая `GetBufferAccesses`, `UnmanagedState`, material/transform/indirect buffers, skinning, SDK history и descriptors. Для исполнения диапазонов нужно согласовать узкий split/resume seam с P2b owner. Он сохраняет общий compiled graph и его resource bindings. На границе выдаёт настоящий DIRECT point после GPU joins локальных COMPUTE readers участка. Первая версия может join весь COMPUTE данного участка на GPU. Background work с отдельным lifetime в этот join не входит. Внешний план получает только явно перечисленные boundary reads/writes и states. Primary-only resources остаются внутри legacy domain. Если ресурс пересекает границу, его access, COMMON переход и состояние после возврата объявляются и учитываются обеими сторонами. `DeclareCompleteAccesses` применяется только к placed проходам после проверки всех физических accesses. Legacy участок не выдаётся за такой pass.

Pack копирует frame-owned depth/normals в отдельный invocation-owned source. Он удерживается до source-copy completion. Обычный legacy transient остаётся под frame lifetime и доступен для reuse после последнего primary reader, включая pack. На обратном пути acquired local slot удерживается до завершения upsample или последнего legacy reader. Если читает legacy участок, его DIRECT receipt покрывает joined async readers. До release состояние ресурса возвращается к согласованной границе. Открытые boundary views не переиспользуются transient pool раньше этого срока. Первыми тестами bridge должны стать реальные early/late links и legacy async read после remote import, проверка отсутствующего access declaration, reuse при задержке COPY и progress независимого primary prefix.

Текущий P2b отвергает mixed placed/legacy plan. P4 доказывает общий dependency/lifetime contract на fully placed synthetic chain. Для production A1 предлагаем согласовать split/resume seam и описанный составной план. До проверки границы production использует local AO. Если разрез не позволяет учесть все пересекающие его ресурсы, перевести соответствующую live closure на explicit declarations перед включением.

P3b принимает buffers и typed single-plane color textures, включая array/mips. Для A1 primary pack читает depth SRV и пишет typed `R32_FLOAT` depth, сохраняя reverse-Z, разрешение выбранного A0 режима и соответствующий normal sample. Secondary возвращает typed `R32_FLOAT` visibility. Проверки включают Full/Half, early/late, odd extents и четыре AO алгоритма из A0. Raw depth, typeless, MSAA и planar остаются за границей P3b.

Для S2 secondary producer рендерит sun cascades, spot slices и все шесть point faces в свои DSV. Export читает depth SRV и переносит согласованные `R32_FLOAT` color regions/slices вместе с matching matrices, splits, stable light key и layout revision. Первый безопасный binding для смешанных local/remote источников — primary restore выбранных regions/slices в существующий depth atlas с записью `SV_Depth` и последующим переходом к sampled state. Локальные регионы сохраняются. Прямой sampled color view допустим после проверки `SampleCmpLevelZero`, array/atlas layout, матриц и всех lighting/transparency/reflection consumers. Fixture проверяет Sun, spot, point, выбор подмножества и пересортировку lights. Текущий `R32_TYPELESS` DSV atlas нельзя передать в P3b как color resource через смену SRV format.

`GDX12TextureDesc::ExternalResource` принимает `GDX12ResourceHandle` для descriptor wrapper над импортированной текстурой. `GDX12Texture::Initialize` создаёт `GDX12TextureResource` с собственным state tracking. Graph `ViewBinding` должен использовать тот же `GDX12Resource`, который видит wrapper, либо согласованный перенос единственного tracker на границе COMMON. COPY transport и consumer передают владение через issued points. Два независимых mutable tracker для одной native view создадут неверные barriers. View/descriptor удерживает bank owner и reader lease до receipt. При reconfigure снять bindings и retire descriptors до замены bank.

## Controls и пресеты

`docs/plans/2026-11-09-quality-presets-benchmark-plan.md`, раздел 5, разделяет quality/budget и execution alternatives. Реальная MGPU switch получает `false` default. Регистрируем её вместе с работающим маршрутом и проверкой, включая synthetic route для P4 fixture. Для смены device pair первый `applyMode` — `restart-process`, для смены bank/layout — `recreate-technique` после retirement. Live routing возможен для уже созданных устройств, когда подтверждён безопасный frame boundary. Pending ReadOnly value не подменяет active state. Physical LUID выбирается явно. `AdapterId` годится только для текущего runtime.

Состояние содержит requested и active placement/freshness, идентичности активных адаптеров, причину fallback и эффективные параметры. В diagnostics отдельно фиксируем timestamp выбранной публикации на host clock, age, cadence, optional drops, Exact deferrals и transfer bytes. `.Quality`, `Render.AO.Resolution`, симуляционные бюджеты и execution switches принадлежат разным осям. Пресет меняет только owned values. Startup settings и временные пробы используют предусмотренный registry/overlay с validation и rollback, без per-key autosave. Fallback сохраняет качество и simulation cadence, пока техника не получила отдельную явную настройку.

## Handoff

Ведущему принять P2b/P3b/A0 commits, сверить injection, copy recording, reader admission и partial-submit contract, согласовать границу legacy/placed для первого production consumer. После этого интегратор регистрирует production sources, реализует P4 и проверяет обычный App fallback, CPU settings/lifetime checks и native strict/background chain на двух физических адаптерах. Workloads требуют `owner=Integrator`, `state=granted`, точного worktree и сообщения ведущего. Сборки и проверки идут последовательно через peengine-perf runner. Подготовка завершена статически. P4 code и hardware validation относятся к следующему шагу.
