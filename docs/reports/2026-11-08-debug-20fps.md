# Debug Bistro: путь к 20 FPS

8 ноября 2026. Измеренная актуальная версия — `79c8f3b`, ветка
`codex/bistro-rendering`. **Медиана средних времён трёх обычных запусков —
71,128 мс, или 14,06 FPS.** Для 20 FPS нужен кадр 50 мс: убрать 21,128 мс,
то есть 29,70% времени. Оптимизации в этой задаче не внедрялись.

| Обычный Debug, 79c8f3b | мс/кадр | FPS |
|---|---:|---:|
| Запуск 1 | 68,511 | 14,60 |
| Запуск 2 | 71,479 | 13,99 |
| Запуск 3 | 71,128 | 14,06 |

Это 300 измеряемых кадров после 120 прогревочных в каждом свежем процессе.
Медиана относится к **средним по запускам**, не к отдельным кадрам.
Показатели обычного executable отделены от диагностического профиля и Nsight.

## Условия и границы сравнения

Ryzen 7 5800HS, RTX 3060 Laptop 6 GiB, Windows 11, Debug/x64. Сохранены
`/Od`, `/RTC1`, `/MDd`, `_DEBUG`; без `-d3ddebug`. Стартовая камера
(-300, 200, 20), rotation (0, 117, 0), окно 1280×800, Render.NumFrames=3,
панель Settings открыта, Bounds=false, физика ×1, particles ×2 / бюджет
500 000, NPC=10, fox=5, grass budget=60 000. Это полный существующий
сценарий, без уменьшения эффектов, частоты анимации или качества физики.

Runtime INI содержит только Render.NumFrames и App.Bounds.Show; остальные
значения берутся из кода. SHA256 INI:
`53c782371018e3e7e00f43d7d41594de0112be828a89277c076651a86b16e245`.
Обычный executable 79c8f3b:
`1a606367893e67b1acb528762b9f060966a25ca075d191857dc0922ef83c4b4b`.
Все шесть обычных запусков и диагностический запуск завершились с exit 0,
неизменными fingerprints executable/INI и ожидаемыми счётчиками кадров.
Бенчмарки и наши сборки выполнялись последовательно.

В начале незавершённая рабочая версия маршрутов завершилась ошибкой
`Bistro human route lost its walkable ground`. Этот запуск исключён.
Для исследования были заморожены application-исходники `17355a1` в Build,
без отката рабочего дерева. Его три обычных запуска дали
64,472 / 78,301 / 68,761 мс. Затем параллельная работа создала `79c8f3b`;
он пересобран штатным MSBuild и измерен отдельно в таблице выше.
Позднейшие незакоммиченные изменения BistroPeopleLoop/BistroWaterLayout,
созданные уже после сборки в 02:48:50 МСК, в измеренный executable не входят.
Не следует приписывать разницу серий исключительно маршрутам.

**Подробный CPU-профиль и GPU Trace ниже относятся к 17355a1**, а не к
79c8f3b. Основные участки renderer между ними не менялись, но точный профиль
новых маршрутов не снят. Обычный App использует random_device для персонажей;
его seed не заморожен. В диагностической копии seed=12345, seed физических
волн=12345. Фазы симуляции в realtime-запусках не тождественны.
Частоты не фиксировались. Это ограничивает причинные сравнения небольших
различий. В ранней серии GPU нагрелась с 52 до 79 °C; после длинного
диагностического прогона было 84 °C. Измерений CPU clocks нет.

## Где уходит CPU

Отдельный диагностический executable: 120 прогревочных + 900 измеряемых
кадров. Среднее update+render=86,22 мс, p50=74,56, p95=110,69 мс;
обычный benchmark total=86,97 мс/кадр. Эти числа **не подменяют** обычный
FPS: отличаются длина окна, состояние физики, seed и наличие таймеров.

| Участок | Среднее, мс/кадр | Что установлено |
|---|---:|---|
| Физика целиком | 21,50 | Jolt 16,95; остальная работа fixed update около 4,55 |
| Scene snapshot | 14,42 | extraction 6,31 + aggregation 7,85; оба уже включены в 14,42 |
| Запись Local shadows | 11,76 | Главный CPU pass; включает application geometry, включая grass |
| Построение UI | 6,28 | BeginFrame почти полностью состоит из UI; отрисовка UI-команд всего 0,05 |
| Skeletal preparation | 5,35 | Анимация и подготовка геометрии персонажей |
| ECS movement | 1,51 | Все соответствующие scheduled системы и их ожидание |
| Grass views preparation | 1,03 | Подготовка view, не вся стоимость травы |
| Shadow visibility wait | 0,35 | Уже небольшой участок; не основной резерв |

Таблица содержит отдельные участки; scene snapshot входит в pipeline preparation,
а Local shadows — в graph_total=16,97 мс. Родительские и вложенные scopes
не складываются повторно. Worker-duration sums здесь не используются.

В Present обнаружено 38 кадров из 900 с задержкой >10 мс, максимум 512,93 мс.
Среднее Present=11,01 мс при медиане 0,317 и p95=0,538 мс. Причина длинных
остановок не установлена; это не доказательство включённого VSync или нехватки
GPU. VSync в trace выключен. Первая треть длинного профиля заметно тяжелее
последующих: update+render 97,39 / 79,64 / 81,63 мс по окнам 300 кадров.

## GPU: вода и тени

Nsight Graphics 2026.4, восемь кадров начиная с frame 199, Throughput Metrics,
Time Every Action, clocks unaltered, одна наблюдаемая queue. Средний интервал
кадра trace=67,28 мс. Он включает простои и не равен сумме GPU-работы.

| GPU-маркер | Среднее, мс/кадр |
|---|---:|
| Fluid simulation / SPH | 14,95 |
| Local shadows целиком | 11,78 |
| Sun shadows | 6,79 |
| GPU particles draw | 2,49 |
| Sorted/additive HDR composition | 2,06 |
| GBuffer | 1,34 |
| SSR | 1,28 |
| XeSS | 0,98 |

Это интервалы маркеров из отдельного инструментированного trace; они могут
включать ожидания. Дублирующие parent/child строки в таблице не суммируются.
GR cycles active = 64,36–72,01% по кадрам: у GPU есть простои, но запас не
неограничен. Из процентов throughput нельзя вывести единственную причину
ограничения или обещание выигрыша async compute.

В одной из 216 строк Local shadow draw экспорт содержит возрастающие значения
до 468,7 мс, превышающие целый кадр. Строка полностью исключена из дочерней
разбивки; доверять автоматическому «23,95 мс Local shadow draw» нельзя.
Валидный **родительский Local shadows=11,78 мс** сохранён. 215 оставшихся
draw-строк дают 6,80 мс, это неполный итог дочернего маркера. Cull=1,53 мс,
clear=0,34 мс, copy=0,60 мс; они входят в parent, не добавляются к нему.

Короткий Bistro grass simulation=0,011 мс не означает, что трава бесплатна:
`BistroGeometryPass::Execute` вызывает Expand для каждого подходящего view
внутри теневых и прочих геометрических проходов. Новая разбивка expansion
нужна перед выбором конкретной GPU-оптимизации травы.

Экспорт Nsight завершён с rc=0 в BASE_UNLOCKED. Capture-wrapper ошибочно
ожидал BASE и вернул 4. Read-only binary analyzer не поддерживает WRPV v11;
использован штатный TSV export с проверкой восьми столбцов и границ длительностей.
Один испорченный вложенный marker явно сохранён в gpu.json как excluded.
Нового capture ради этой известной ошибки оболочки не выполнялось.

## Физика: 20 FPS не гарантируют realtime

В диагностическом измеряемом окне запрошено 78,229 с физического времени,
выполнено 2507 fixed ticks / 41,783 с. Долг вырос с 2,312 до 38,758 с;
его прирост 36,446 с совпадает с requested−simulated с точностью округления.
Всего 950 тел, active bodies в конце тика 69–947. Wall-budget достигался
на всех 900 измеренных кадрах. Jolt: среднее 6,086 мс/tick; по трём окнам
4,200 / 6,960 / 8,020 мс/tick. Это меняющаяся контактная нагрузка, не
доказательство ухудшения самого алгоритма со временем.

В `App::UpdatePhysics` fixed step=1/60, максимум 8 ticks, но break после
достижения 16,67 мс wall time. При дорогих поздних тиках часто помещается
лишь два шага на rendered frame. Поэтому достижение 20 FPS само по себе
ещё может оставить физику около 40 ticks/s. Нельзя скрывать это сбросом
accumulator, уменьшением TimeScale или пропуском физических шагов.
Для устойчивых трёх ticks за текущий wall budget нужна общая стоимость
тика примерно ≤5,56 мс, включая fixed systems; либо отдельно согласованное
изменение распределения бюджета кадра с повторным измерением всей системы.

## Предлагаемый порядок работ

Цели ниже — **бюджеты экспериментов, не измеренные выигрыши**. Их нельзя
вычесть из обычных 71,13 мс как гарантированный результат другого запуска.

1. **Scene snapshot: цель 6–8 мс вместо диагностических 14,4.**
   `RenderModule::CollectReflectionScene` всё ещё проходит submeshes и
   primitives, даже когда cached signature/geometry не изменились. Сначала
   сократить повторные публикации и агрегацию неизменной статики. Использовать
   уже существующий snapshot cache и generational handles. Инвалидация должна
   учитывать удаления, reimport, material/visibility edits, dynamic↔static и
   прямые изменения transform/CPU mirrors. Общий union-only bounds cache
   неверен при удалении крайнего объекта. Владельцы: RenderModule.cpp,
   GDX12RenderGeometry.h. Проверки: ObjectDataJobsTests, RenderPipelineTests.

2. **Local shadows: цель CPU 4–6 мс вместо 11,8 и меньшая GPU-стоимость.**
   В ExecuteGeometryView на каждой dirty face повторяются setup, counter clear,
   dispatch полного `_commandCount`, bindings и ExecuteIndirect. Проверить
   подготовку общих bindings один раз, компактный dynamic template list и
   группировку записи по face. Отдельно измерить grass Expand внутри теней:
   переиспользовать можно только совместимую геометрию с тем же LOD/culling,
   сохраняя все необходимые view. Существующий static visibility cache уже
   работает; расширять его вслепую не нужно. Владельцы: GDX12LocalShadowPass.h,
   BistroRenderPipeline.cpp, Grass GPU geometry. Проверки: LightingGpuTests,
   BistroRenderGraphTests, depth/HDR oracle, moving lights/casters, cube seams.

3. **UI: цель около 1 мс вместо 6,3, при открытой панели.**
   `DrawSettings` каждый кадр получает и сортирует список CVars, конвертирует
   имена и строит дерево map/vector. Кэшировать структуру и подписи до изменения
   регистрации/фильтра; значения читать живыми. Учесть unregister и lifetime
   указателей. Не требуется кэшировать пользовательские значения. Владельцы:
   UI_test.cpp и ConsoleModule.cpp. Сейчас F1 уже скрывает панель — это простой
   временный способ убрать значительную часть этого scope, но отдельный A/B
   для F1 здесь не выполнен и 20 FPS от одного F1 не обещаются.

4. **Skeletal preparation: резерв второго этапа, цель 3–4 мс вместо 5,35.**
   Профилировать pose evaluation отдельно от преобразования bounds и публикации.
   Убирать повторное вычисление для неизменной pose, разделять immutable mesh
   data и frame data. Не снижать animation frequency; при низком FPS pose
   действительно может обновляться каждый кадр, поэтому один pose cache
   проблему не обязательно решит.

5. **Физика — самостоятельный критерий приёмки.** Сначала разделить оставшиеся
   4,55 мс fixed-system overhead и Jolt contacts/solver при одинаковой фазе
   волн и числе активных тел. Цена Jolt в позднем окне уже выше бюджета,
   позволяющего три шага за кадр. Уменьшение CPU renderer полезно, но его
   выигрыш частично может перейти в большее число физических шагов. Не менять
   CCD, collision steps или геометрию без отдельного решения о качестве.

6. **Дешёвый дополнительный эксперимент: существующий async water + particles.**
   `Render.Fluid.AsyncCompute` и `Render.Particles.AsyncCompute` по умолчанию
   false и в измеренном INI не включены. Сначала A/B существующих переключателей,
   без новой архитектуры или задержки N→N+1. Вода стоит 15 мс GPU, но её
   перенос на другую очередь не означает экономию всех 15 мс и не убирает
   21 мс дефицита CPU автоматически. AO не выглядит первым кандидатом.

Практическая первая итерация — пункты 1–3, каждый отдельным вариантом и с
обычным A/B. Для устойчивых 20 FPS нужен запас ниже 50 мс, а не ровно 50 мс
в лучшем запуске. Приёмка: повторные свежие процессы с фиксированными inputs,
обычный frame mean и p95, затем длинный realtime Run с requested/simulated/debt.
Нулевой прирост долга проверяется отдельно от визуального FPS. Дополнительные
сборки/профайлеры не должны работать одновременно с scored runs.

PDB сторонних библиотек. Проверены exit codes, counts, hashes, арифметика долга
и форма GPU export. Production code и настройки не менялись; regression suite,
новый длительный soak и A/B предложенных оптимизаций не выполнялись.
