# Bistro. Подбор DIRECT/COMPUTE за десять минут

## Результат

По кнопке «Бенчмарк» в загруженной Bistro подобрать одну раскладку очередей для текущей видеокарты, разрешения и нагрузки. Пользователь получает измеренный выигрыш относительно штатного дефолта или сообщение, что дефолт сохранён. От нажатия кнопки до применения результата отводится **600 секунд реального времени**, включая прогрев, переключения, измерения и запись результата.

Менять размещение шести групп: AO, Environment, LightGrid, Particles, Water и CloudPicture. Качество эффектов, плотность симуляции, скорость камеры и длительность остановок сохранять для всех сравнений. Выбор адаптера и межкарточные передачи относятся к следующему заданию. Для этого запуска обеспечить локальное исполнение всех участвующих техник на основной карте.

## Откуда начать

В [BistroBenchmark.h](../../Apps/App/src/BistroBenchmark.h) уже есть запуск и отмена, применение маски, маршрут, сбор времени кадров, CSV и применение победителя. Сейчас он выполняет 64 полных пролёта. По умолчанию каждый занимает 3 секунды прогрева и 100 секунд измерения, итого 109 минут 52 секунды до учёта накладных расходов. Сокращение всего маршрута меняет характер нагрузки: пять остановок у картин по-прежнему занимают 25 секунд. Использовать короткие фрагменты исходного маршрута на его обычной скорости. [Маршрут Bistro](../../Apps/App/src/BistroBenchmarkRoute.h)

База сравнения — текущий штатный дефолт: `App.Async.Queues=true`, все шесть переключателей `App.Async.*` из списка выше выключены. При этом граф уже размещает skinning и culling на COMPUTE, а загрузки на COPY. Сохранить это поведение во всех кандидатах. Сравнение проводить при одинаковых настройках одного адаптера, генерации кадров и освещения. Существующий бенчмарк на старте фиксирует только адаптер CloudPicture, генерацию кадров и цикл солнца. [Стартовая конфигурация](../../Apps/App/Configs/Startup.ini) · [Назначения очередей геометрии](../../Apps/App/src/Techniques/SceneGeometry.cpp)

## Порядок поиска

1. **Один полный прогон дефолта.** Сохранить среднее время кадра, p95 и исходные кадры с временем на маршруте. Эти же данные служат эталоном для коротких сравнений. По нескольким заранее определённым фазам маршрута отметить, какие группы действительно исполнялись. Панель Bistro уже читает пакеты действующего расписания. Выключенную технику или технику без работы за весь базовый пролёт можно исключить из поиска. [Панель Bistro](../../Apps/App/src/Techniques/UI/BistroInfoPanel.cpp)
2. **Короткие сравнения.** Выделить воспроизводимые окна с разной нагрузкой, например у фонтана и арки, внутри Bistro и у картины с активной CloudPicture. Для каждой пробы воспроизводить одинаковый вход в окно, движение и состояние влияющих на измерение симуляций и обновлений. Дать истории кадра и очередям стабилизироваться после переключения. Кадры прогрева исключить. Неактивность техники на одном участке не исключает её на остальных.
3. **Ограниченный поиск сочетаний.** Начать с одиночных переносов активных групп. На тех же окнах проверить совместное включение лучших одиночных переносов и несколько пар, в том числе пару без одиночного выигрыша. Это позволяет увидеть взаимодействие техник при конкуренции за GPU. При выборе дополнительных пар отдавать приоритет группам, работающим в одной фазе. Если осталось время, у двух лидеров добавить или убрать по одному флагу. Вести множество измеренных масок. Дополнительное время отдавать проверке лидеров на других окнах. Порядок разрешения равных оценок сделать воспроизводимым.
4. **Сопоставимая оценка.** Сравнивать кандидатов на одном наборе окон с дефолтом на тех же отрезках. При ранжировании учитывать долю соответствующих фаз в полном пролёте. Выделить короткий повтор базовых окон для оценки разброса при неизменной раскладке. Сравнить среднее и p95 сопоставимых окон двух измерений дефолта. Изменения нагрузки между разными участками маршрута не считать шумом. Не усреднять оконные p95 для получения p95 всего маршрута.
5. **Один полный прогон финалиста.** Выбрать лидера коротких сравнений, если у него есть преимущество над дефолтом. Пройти тот же полный маршрут с тем же прогревом. Применить раскладку, только если снижение среднего времени кадра превышает оценённый разброс, а рост p95 укладывается в установленный допуск. Взять для первой реализации больший из минимального допуска и наблюдаемого относительного разброса базовых окон, отдельно для среднего и p95. Стартовые минимумы для реализации — 1% для среднего и 2% для p95. Вывести фактические пороги в отчёт. При неопределённом результате, недостатке сопоставимых данных или времени оставить дефолт. Полный прогон дефолта повторно не требуется.

## Бюджет и управление

Использовать монотонные часы для общего дедлайна. Счётчик времени измеренных кадров в существующем бенчмарке пропускает часть работы приложения и для этой цели непригоден. На стандартном маршруте два прогрева и два пролёта требуют номинально 206 секунд. Оставшиеся 394 секунды включают все короткие пробы и накладные расходы.

После базового прогона зарезервировать на финал фактическую длительность базы по настенным часам с запасом на завершение. Перед каждой пробой проверять, что в бюджет помещаются её прогрев, измерение, финал и применение результата. Проверять дедлайн и во время измерений. При нестандартной длительности маршрута или медленном кадре сокращать число проб. При нехватке времени для подтверждения закончить с дефолтом. Если уже базовый прогон не помещается в бюджет, сообщить об этом без применения неподтверждённой раскладки.

Сохранить существующую семантику отмены: вернуть настройки и камеру, которые были до нажатия кнопки. После штатного завершения оставить выбранную раскладку и восстановить временные настройки бенчмарка. Показать в панели текущую фазу, прошедшее время и выбранную раскладку.

## Результат разработки и приёмка

Расширить текущий CSV, чтобы по одному запуску можно было увидеть длительность поиска, этап и маску каждой пробы, измеренные участки, число кадров, среднее и p95 в миллисекундах. Для финала записать базу, финалиста, разницу, пороги и причину применения раскладки или сохранения дефолта. Использовать один и тот же способ измерения кадра в обеих полных выборках. Текущая метрика измеряется на CPU вокруг части обновления и рендера с Present. Загрузка COMPUTE или сумма длительностей пакетов не служат критерием победы.

Для приёмки достаточно одного обычного запуска из панели Bistro. По результату должны быть видны полный эталон, сокращённый набор коротких проб, максимум один полный финалист, итоговая раскладка и длительность до 600 секунд. Сохранение дефолта с измеренной причиной — штатный результат. Поиск выдаёт лучшую подтверждённую раскладку среди проверенных. Исчерпывающее доказательство глобального оптимума, подбор качества и MGPU находятся за рамками задания.
