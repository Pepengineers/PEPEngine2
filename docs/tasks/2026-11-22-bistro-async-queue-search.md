# Bistro. Подбор DIRECT/COMPUTE за десять минут

## Результат

В Release после загрузки Bistro автоматически подобрать одну раскладку очередей для текущей видеокарты, разрешения и нагрузки. В Debug пользователь запускает подбор из панели. Пользователь получает измеренный выигрыш относительно штатного дефолта или сообщение, что дефолт сохранён. От автоматического старта в готовой сцене или нажатия кнопки до применения результата отводится **600 секунд реального времени**, включая прогрев, переключения, измерения и запись результата.

Менять размещение шести групп: AO, Environment, LightGrid, Particles, Water и CloudPicture. Качество эффектов, плотность симуляции, скорость камеры и длительность остановок сохранять для всех сравнений. Выбор адаптера и межкарточные передачи относятся к следующему заданию. Для этого запуска обеспечить локальное исполнение всех участвующих техник на основной карте.

## Запуск и кнопки

| Сборка и параметры запуска | После готовности сцены | Действия в панели Bistro |
|---|---|---|
| Release по умолчанию | Один автоподбор при каждом запуске приложения | «Автоподбор» и «Прогон» |
| Release с аргументом `-SkipBenchmark` или CVar `App.Benchmark.SkipBenchmark=true` | Сразу передать управление пользователю | Те же две кнопки |
| Debug | Сразу передать управление пользователю | Те же две кнопки |

Прочитать стартовую CVar (по умолчанию `false`) из обычной конфигурации приложения. Аргумент `-SkipBenchmark` подавляет автозапуск и при значении CVar `false`. Ручная команда «Автоподбор» всегда доступна в свободной панели и запускает тот же поиск, что Release. Автоматический старт выполнить один раз за жизнь процесса после подготовки сцены и камеры. Ручной запуск можно повторять. После отмены или ошибки вернуть управление пользователю. Пока выполняется любое из двух действий, показать прогресс и кнопку отмены. [Инициализация Bistro](../../Apps/App/src/BistroApplication.cpp) · [Панель Bistro](../../Apps/App/src/Techniques/UI/BistroInfoPanel.cpp)

**«Прогон»** выполняет один полный маршрут с обычным прогревом и сохраняет отдельный CSV на текущих пользовательских CVars. Сохранить выбранные пользователем режимы очередей, адаптеры, разрешение, реконструкцию, генерацию кадров и настройки эффектов. Патч настроек для автоподбора применять только при запуске поиска. После прогона вернуть камеру и управление, показать путь к файлу. Пользователь может изменить CVar и сразу выполнить следующий прогон. Перенести из текущего бенчмарка управление маршрутом и сбор статистики в общий для обеих кнопок код. Удалить цикл по 64 маскам, его ETA и прежний выбор победителя.

## Откуда начать

В [BistroBenchmark.h](../../Apps/App/src/BistroBenchmark.h) уже есть запуск и отмена, применение маски, маршрут, сбор времени кадров, CSV и применение победителя. Сейчас он выполняет 64 полных пролёта. По умолчанию каждый занимает 3 секунды прогрева и 100 секунд измерения, итого 109 минут 52 секунды до учёта накладных расходов. Сокращение всего маршрута меняет характер нагрузки: пять остановок у картин по-прежнему занимают 25 секунд. Использовать короткие фрагменты исходного маршрута на его обычной скорости. [Маршрут Bistro](../../Apps/App/src/BistroBenchmarkRoute.h)

База сравнения — текущий штатный дефолт: `App.Async.Queues=true`, все шесть переключателей `App.Async.*` из списка выше выключены. При этом граф уже размещает skinning и culling на COMPUTE, а загрузки на COPY. Сохранить это поведение во всех кандидатах. Сравнение проводить при одинаковых настройках одного адаптера, генерации кадров и освещения. Существующий бенчмарк на старте фиксирует только адаптер CloudPicture, генерацию кадров и цикл солнца. [Стартовая конфигурация](../../Apps/App/Configs/Startup.ini) · [Назначения очередей геометрии](../../Apps/App/src/Techniques/SceneGeometry.cpp)

## Порядок поиска

1. **Один полный прогон дефолта.** Сохранить среднее время кадра, p95 и исходные кадры с временем на маршруте. Эти же данные служат эталоном для коротких сравнений. По нескольким заранее определённым фазам маршрута отметить, какие группы действительно исполнялись. Панель Bistro уже читает пакеты действующего расписания. Выключенную технику или технику без работы за весь базовый пролёт можно исключить из поиска. [Панель Bistro](../../Apps/App/src/Techniques/UI/BistroInfoPanel.cpp)
2. **Короткие сравнения.** Выделить воспроизводимые окна с разной нагрузкой, например у фонтана и арки, внутри Bistro и у картины с активной CloudPicture. Для каждой пробы воспроизводить одинаковый вход в окно, движение и состояние влияющих на измерение симуляций и обновлений. Дать истории кадра и очередям стабилизироваться после переключения. Кадры прогрева исключить. Неактивность техники на одном участке не исключает её на остальных.
3. **Ограниченный поиск сочетаний.** Начать с одиночных переносов активных групп. На тех же окнах проверить совместное включение лучших одиночных переносов и несколько пар, в том числе пару без одиночного выигрыша. Это позволяет увидеть взаимодействие техник при конкуренции за GPU. При выборе дополнительных пар отдавать приоритет группам, работающим в одной фазе. Если осталось время, у двух лидеров добавить или убрать по одному флагу. Вести множество измеренных масок. Дополнительное время отдавать проверке лидеров на других окнах. Порядок разрешения равных оценок сделать воспроизводимым.
4. **Сопоставимая оценка.** Сравнивать кандидатов на одном наборе окон с дефолтом на тех же отрезках. При ранжировании учитывать долю соответствующих фаз в полном пролёте. Выделить короткий повтор базовых окон для оценки разброса при неизменной раскладке. Сравнить среднее и p95 сопоставимых окон двух измерений дефолта. Изменения нагрузки между разными участками маршрута не считать шумом. Не усреднять оконные p95 для получения p95 всего маршрута.
5. **Один полный прогон финалиста.** Выбрать лидера коротких сравнений, если у него есть преимущество над дефолтом. Пройти тот же полный маршрут с тем же прогревом. Применить раскладку, только если снижение среднего времени кадра превышает оценённый разброс, а рост p95 укладывается в установленный допуск. Взять для первой реализации больший из минимального допуска и наблюдаемого относительного разброса базовых окон, отдельно для среднего и p95. Стартовые минимумы для реализации — 1% для среднего и 2% для p95. Вывести фактические пороги в отчёт. При неопределённом результате, недостатке сопоставимых данных или времени оставить дефолт. Полный прогон дефолта повторно не требуется.

### Отсев между короткими пробами

После первого набора коротких окон отсортировать измеренные маски по выигрышу относительно базы на тех же участках. Оставить примерно половину и расширить измерение выживших в следующем раунде. Формировать пары можно до первого отсева, чтобы сохранить вариант, который выигрывает только при совместном переносе. Сравнивать кандидатов внутри одного раунда на одинаковом наборе окон. Последовательность 8 → 4 → 2 → 1 иллюстрирует порядок при восьми кандидатах. Число проб зависит от активных групп и оставшегося времени.

На границе сравнить последнего проходящего и первого выбывающего. Если разница их оценок укладывается в измеренный разброс базовых окон, дать обоим один дополнительный замер на одинаковом окне и пересчитать порядок с учётом новых данных. Когда различающая кандидатов техника ещё не проявилась на измеренных участках, выбрать общее окно, где она активна. При повторной ничьей применять воспроизводимое правило. До старта пары проб зарезервировать реальное время на обе и полный финал. Если пары уже не помещаются, выбрать среди сопоставимых данных и явно записать причину пропуска. CSV должен позволять восстановить состав раунда, границу, причину и результат дополнительного замера. Окончательно применять кандидата только по полному пролёту в рамках общего лимита 600 секунд.

Так мы адаптируем поэтапное сокращение числа кандидатов и дополнительное измерение спорных вариантов к сценам Bistro. [Successive Halving](https://proceedings.mlr.press/v51/jamieson16.html) · [Rasulo и др., гибридный отсев, GECCO 2026](https://doi.org/10.1145/3795095.3805134)

## Бюджет и управление

Использовать монотонные часы для общего дедлайна. Счётчик времени измеренных кадров в существующем бенчмарке пропускает часть работы приложения и для этой цели непригоден. На стандартном маршруте два прогрева и два пролёта требуют номинально 206 секунд. Оставшиеся 394 секунды включают все короткие пробы и накладные расходы.

После базового прогона зарезервировать на финал фактическую длительность базы по настенным часам с запасом на завершение. Перед каждой пробой проверять, что в бюджет помещаются её прогрев, измерение, финал и применение результата. Проверять дедлайн и во время измерений. При нестандартной длительности маршрута или медленном кадре сокращать число проб. При нехватке времени для подтверждения закончить с дефолтом. Если уже базовый прогон не помещается в бюджет, сообщить об этом без применения неподтверждённой раскладки.

Сохранить существующую семантику отмены: вернуть настройки и камеру, которые были до нажатия кнопки. После штатного завершения оставить выбранную раскладку и восстановить временные настройки бенчмарка. Показать в панели текущую фазу, прошедшее время и выбранную раскладку.

## CSV прогона и сравнение двух режимов

В DX12-референсе `BenchmarkState::Tick` накапливает кадры и время до границы примерно в одну секунду. В конце интервала он берёт число кадров за FPS, вычисляет `MSPF = 1000 / FPS` и обновляет накопленные экстремумы интервальных значений. SSR ставит в очередь строку из шести полей `FPS;MSPF;MinFPS;MinMSPF;MaxFPS;MaxMSPF`. При выходе из режима `FileQueueWriter` записывает накопленные строки в файл. [Сбор DX12](https://github.com/Mikhanil/Multi-GPU-Render-DX12/blob/d17e45bcfef0a16af0f7ee74e936c162845bd221/Common/Services/States/BenchmarkState.h) · [Формат строки](https://github.com/Mikhanil/Multi-GPU-Render-DX12/blob/d17e45bcfef0a16af0f7ee74e936c162845bd221/Common/Utils.h) · [Запись при выходе](https://github.com/Mikhanil/Multi-GPU-Render-DX12/blob/d17e45bcfef0a16af0f7ee74e936c162845bd221/MGPU-SSR/States/ReflectionBenchmarkState.cpp)

Каждый ручной прогон пишет новый CSV в существующий каталог `BenchmarkResults` рядом с исполняемым файлом. Полные пролёты автоподбора используют те же определения метрик. Сохранить запятую как разделитель и один заголовок для всего файла. Различать строки по полю `type`.

| Тип строки | Что записывать |
|---|---|
| `config` | Идентификатор запуска, сборку, режим запуска, версию и длительность маршрута. По одной паре имя/значение для действующих CVars рендера и нагрузки, включая шесть флагов и общий переключатель очередей. Записать фактические адаптеры, разрешение и режим реконструкции/FG, чтобы различать прогоны после ручных правок. |
| `frame` | Каждый измеренный кадр без прогрева: номер, участок, `route_seconds`, `frame_ms`. Сохранить существующую границу `frame_ms` для оценки кандидатов. Для частоты кадров приложения писать также `frame_interval_ms` по монотонным отметкам между последовательными возвратами из Render с Present. Начальную отметку взять на границе прогрева. При включённой FG счётчик отражает кадры приложения. |
| `interval` | Примерно раз в секунду маршрута: начало и конец окна, число кадров и шесть показателей DX12. Для N кадров с суммой `frame_interval_ms` равной T миллисекунд считать `FPS = 1000 × N / T` и `MSPF = T / N`. Min/Max накапливать по завершённым окнам данного пролёта. Группировать кадры по одинаковым границам маршрутного времени для всех режимов. |
| `summary` | Статус, измеренную длительность, число кадров, среднее и p95 по исходным `frame_ms`. Для прерванного прогона сохранить собранные строки и статус `cancelled`. |

Сравнивать два файла по версии маршрута, участку и времени от начала движения: разный FPS даёт разное число кадров на одном отрезке. Во время измерения накапливать строки в памяти или буферизовать запись. Закрывать файл при завершении и отмене. Показать ошибку записи в панели, если сохранить данные не удалось.

## Результат разработки и приёмка

Расширить текущий CSV, чтобы по одному запуску можно было увидеть длительность поиска, этап и маску каждой пробы, измеренные участки, число кадров, среднее и p95 в миллисекундах. Для финала записать базу, финалиста, разницу, пороги и причину применения раскладки или сохранения дефолта. Использовать один и тот же способ измерения кадра в обеих полных выборках. Текущая метрика измеряется на CPU вокруг части обновления и рендера с Present. Загрузка COMPUTE или сумма длительностей пакетов не служат критерием победы.

Для приёмки автоподбора достаточно одного обычного запуска. По результату должны быть видны полный эталон, сокращённый набор коротких проб, максимум один полный финалист, итоговая раскладка и длительность до 600 секунд. Сохранение дефолта с измеренной причиной — штатный результат. Проверить условия запуска по таблице выше. Для ручного сценария открыть панель при пропущенном автоподборе, выполнить «Прогон», изменить одну CVar и повторить. Оба CSV должны сохраниться с разными именами, отразить изменение настройки и позволить сопоставить время кадра на одинаковом участке. Длительный поиск повторять для проверки кнопок не требуется.
