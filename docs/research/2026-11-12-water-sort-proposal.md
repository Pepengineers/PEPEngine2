# Сокращение числа вызовов сортировки воды

Дата: 12 ноября 2026. Результат этого этапа — исследование, компилируемый
экспериментальный шейдер и проверка алгоритма на CPU. Рабочий solver не изменён.

## Рекомендуемый первый эксперимент

Оставить текущую bitonic-сортировку с полным сравнением `(bucket key, particle index)`,
но перенести начальные стадии и короткие хвосты каждого слияния в groupshared memory.
Это сохраняет буферы, порядок обхода соседей и контракт DIRECT/COMPUTE/MGPU.
Сравнить блоки 512, 1024 и 2048 на GPU; размер 2048 не назначается победителем
только потому, что у него меньше dispatch.

Такое разделение глобальных и локальных стадий применяется в
[Microsoft MiniEngine](https://github.com/microsoft/DirectX-Graphics-Samples/blob/master/MiniEngine/Core/BitonicSort.cpp).
Наш прототип сохраняет собственный порядок `(key,index)` и исходную сеть сравнений.
Он не копирует порядок полей и сравнение только ключей из sample.

Для 51 975 частиц `Capacity=65536`:

| Вариант | Sort dispatch / подшаг | Sort dispatch / 3 подшага | Все dispatch / Record с 3 подшагами |
|---|---:|---:|---:|
| Исходная глобальная сеть | 136 | 408 | 421 |
| Hybrid, блок 256 | 45 | 135 | 148 |
| Hybrid, блок 512 | 36 | 108 | 121 |
| Hybrid, блок 1024 | 28 | 84 | 97 |
| Hybrid, блок 2048 | 21 | 63 | 76 |

Последний столбец включает Hash, BuildOffsets, Densities, Integrate на каждом
подшаге и один SavePrevious на Record. Расчёт относится к существующему пути
без дополнительных copy-dispatch. Это число команд, не прогноз времени кадра.

Для `Capacity=2^L`, `B=2^b`, `m=max(0,L-b)`:
исходная сортировка — `L(L+1)/2`; эксперимент — `1+m(m+3)/2`.
При `Capacity=1` сортировку можно вообще не запускать; прототип допускает один
безопасный presort, чтобы проверить граничный случай.

## Конкретная интеграция после проверки кандидата

В `GDX12FluidSolver::Initialize` создать два дополнительных PSO.
В `Record`, после существующего Hash и его UAV-барьера:

```text
PresortCS: ceil(Capacity / B) групп; keys UAV barrier
for k = 2*B; k <= Capacity; k *= 2:
    for j = k/2; j >= B; j /= 2:
        существующий Sort(k,j); keys UAV barrier
    MergeTailCS(k): ceil(Capacity / B) групп; keys UAV barrier
существующий переход keys в SRV и BuildOffsets
```

Минимальная область production-правки: FluidSolver.hlsl, GDX12Fluid.cpp и
GDX12FluidSolver.h. Не менять Hash, соседние ячейки, плотность/силы, SavePrevious,
Head.Current, publication и staged-head commit. Пять solver default-буферов
по-прежнему должны входить/выходить из PlacedUav в UAV-состоянии.

Каждый поток владеет обоими элементами одной пары; барьер следует за каждой
стадией. Не делать ранний return части потоков перед group barrier. Направление
сортировки определяет глобальный индекс: соседние исходные блоки должны иметь
чередующееся направление. Хеш-коллизии не отменяют проверку реальной Cell у соседей.

## Альтернативы с меньшим числом вызовов

[Отдельное исследование первоисточников](2026-11-12-water-sort-primary-sources.md)
содержит ссылки, расчёты и ограничения современных вариантов:

- Уже подключённый FidelityFX Parallel Sort: 20 dispatch для 16 значимых битов.
  Стабильная сортировка входа в порядке particle index сохраняет текущие ties.
  Требуются scratch/ping-pong буферы и расширение описаний ресурсов обоих путей
  solver, а также проверка wave capabilities именно producer-адаптера.
- GPUSorting DeviceRadixSort: расчётно 7 dispatch после адаптации к 16 битам;
  перенос существенно шире. Это следующий кандидат, если hybrid не даёт
  достаточного выигрыша полного подшага.
- OneSweep: потенциально меньше проходов, но межгрупповое ожидание требует
  гарантий forward progress. Не выбирать общим D3D12 вариантом без проверки
  поддерживаемых адаптеров и fallback.
- Histogram/scan/atomic scatter строит нужные buckets без comparison sort,
  но меняет порядок индексов и FP-суммирования. Его можно рассматривать при
  отдельном допуске на изменение поведения симуляции, а не как точную замену.

## Условия принятия

1. GPU readback всех пар и offsets против CPU oracle: 1/2/3, B±1, 2B±1,
   51 975, максимальный count; одинаковые ключи, обратный порядок, max bucket,
   пустые buckets, hash collisions, повторное использование буферов.
2. Совпадение обеих particle buffers и плотности с исходной сетью после одного
   и нескольких шагов при неизменной арифметике. Межблочная interacting-сцена
   обязательна: существующие маленькие fixtures не покрывают слияния.
3. DIRECT/COMPUTE toggle, PlacedUav, Exact/Latest MGPU и полное содержимое
   снимков, а не только первая частица. D3D12 debug layer/GPU validation.
4. Парные замеры CPU записи, GPU sort, Densities, Integrate и всего кадра,
   одинаковые exe/config/camera/seed/counts, повторения. Измерять блоки отдельно,
   сохранить исходный бинарник и исключить одновременные GPU-прогоны других чатов.

GPU-измерениями в текущей параллельной работе владеет отдельный чат диагностики.
До этих проверок прототип остаётся экспериментом и не меняет поведение Bistro.
