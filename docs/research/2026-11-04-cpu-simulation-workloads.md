# Масштабируемая CPU-симуляция: Jolt и навигационные агенты

Дата: 2026-11-04. Статус: исследование и обсуждение требований; перенос кода не начат.

## Согласованная цель

Оценивать производительность на разных системах через полезную игровую работу,
объём которой легко менять под оборудование. Всё работает внутри Bistro.
Нужен механизм масштабирования количества объектов/агентов при спавне по образцу
частиц; пользователь отдельно подберёт пресеты по результатам на разных машинах.
Автоподбор нагрузки, поиск предела машины и отдельная сцена в объём не входят.
Кандидаты — физические взаимодействия тел и навигация агентов, а не холостое
умножение матриц. Термин
«симуляционная нагрузка бенчмарка» добавлен в корневой CONTEXT.md.

## Что есть в JoltPhysics

Это CPU-физика. В
[`JoltPhysicsBackend.cpp`](https://github.com/Pepengineers/PEPEngine2/blob/334df2e33bb8cdf8eca7edb7a90f87b91c6190e8/Apps/App.Base/src/Physics/JoltPhysicsBackend.cpp#L225)
создаётся собственный `JPH::JobSystemThreadPool`: обычно hardware threads минус
один worker. `Step()` синхронно вызывает `PhysicsSystem::Update` с этим пулом.
Это соответствует [архитектуре Jolt](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md):
шаг симуляции разбивается на CPU jobs.

В [PhysicsStress1000.world](https://github.com/Pepengineers/PEPEngine2/blob/334df2e33bb8cdf8eca7edb7a90f87b91c6190e8/Worlds/PhysicsStress1000.world)
есть 1000 динамических, 32 статических и 7 кинематических тел. Полосы пола и ротор
создают продолжающиеся взаимодействия. Это готовая основа нагрузки, но пока
сцена Editor, не автоматический измерительный сценарий. Устойчивость длительной
нагрузки и фактическое число активных тел не измерены.

Переносить следует backend/types и рецепт сцены, адаптируя их к текущему движку.
На исходном HEAD ветки расходились на 203 коммита только Bistro и 39 только Jolt.
Важные несовместимости:

- В Jolt SceneManager владеет fixed-step loop с шагом 1/60; сейчас порядок
  обновления задаёт App, системы поддерживают ParallelJob. Нужен один владелец
  шага и явные фазы input → physics → публикация transforms → render preparation.
- Jolt pool не использует нашу enkiTS JobSystem. Второй почти полный пул может
  конкурировать с первым; обёртка всего Update в один ParallelJob этого не меняет.
- Для общего пула нужен настоящий адаптер Jolt JobSystem. Наш
  [JobSystem.cpp](../../Engine/Engine.Core/src/Jobs/JobSystem.cpp) разрешает
  Schedule/Complete только owner thread; механическая передача worker callbacks
  в этот API не подходит. Следует отдельно проверить зависимости, lifetime jobs,
  barrier/wait и возможность исполнения готовых работ при ожидании.
- В backend сейчас пределы 2048 тел, 16384 пар и 16384 contact constraints,
  временный allocator 10 MiB. Масштабирование выше текущего сценария потребует
  явной настройки ёмкостей и обработки переполнений, а не только увеличения N.
- ECS↔physics синхронизация последовательная; fixed-step catch-up не ограничен.
  При перегрузе возможен рост числа догоняющих шагов. Результат должен показывать
  отставание симуляции, а не скрывать его пропуском работы.
- Есть primitive shapes; интеграция collider полной геометрии Bistro не найдена.
  Для Bistro нужны proxy colliders либо mesh shapes и проверка масштаба координат.
- Ветка несёт готовые Jolt.lib и submodule: при переносе нужны проверки ABI,
  compile defines и сборки. Автотестов физики в diff ветки не найдено.

## Проверка предположения об упоре в GPU

Последний [отчёт после пакетного копирования теней](2026-11-04-shadow-copy-batching.md)
содержит следующие PIX-результаты при обычных частотах:

| Метрика, медиана | Release optimized | Debug optimized |
| --- | ---: | ---: |
| CPU graph recording | 4,846 мс | 33,459 мс |
| GPU command-list envelope | 24,581 мс | 24,658 мс |
| Промежуток между GPU-пакетами | 0,101 мс | 27,139 мс |

В Release оболочки GPU-пакетов занимают 99,60% выбранного окна. Это поддерживает
GPU bottleneck для измеренной конфигурации; в Debug остаётся ограничение CPU.
Оболочка включает внутренние паузы и не равна аппаратному utilisation counter.
Замеры предшествуют свежему распараллеливанию персонажей/поз и текущим правкам
async particles. Для текущего EXE нужен новый baseline.

Гипотеза «job system почти не используется» слишком сильная. Она уже обслуживает
системы движения, GPU object data, shadow visibility, CPU light grid, позы скелетов
и движение персонажей. Однако степень занятости workers не измерена.

В снимке `052ef87` [BistroCharacters.h](../../Apps/App/src/BistroCharacters.h) по умолчанию 4 человека
и 1 лиса, пределы 16 и 8. Есть два parallel этапа, проверка взаимного разделения,
ожидание/разворот и остановка анимации. Это небольшая нагрузка; простое увеличение
лимита масштабирует текущий попарный O(N²) обход. Маршруты заданы вручную,
NavMesh/Recast/Detour в проверенных исходниках и зависимостях не найден.

Во время обсуждения параллельная работа изменила BistroCharacters.h в рабочем
дереве: начальные количества стали 10 NPC и 5 лис, спавн — однократным, движение —
групповым по маршрутам. Это ещё не навигационная симуляция; прежние ограничения
16/8 и попарный обход описывают именно проверенный commit, не новые рабочие правки.
При реализации нужно опираться на итог этого изменения и не дублировать настройки
начального количества.

## Вариант навигации

[Recast/Detour](https://github.com/recastnavigation/recastnavigation) разделяет
построение NavMesh, поиск путей и симуляцию толпы. Полезная runtime-нагрузка:
выбор целей → поиск/перестроение пути → движение по пути → локальный обход соседей
и препятствий. Само наличие NavMesh не создаёт тяжёлую работу каждый кадр.

По [исходнику DetourCrowd](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp)
обычный dtCrowd::update выполняет последовательные этапы/циклы без нашего scheduler.
Это удобный функциональный baseline, но не готовый многопоточный benchmark.
Нельзя одновременно вызывать update одного crowd из нескольких jobs.

Для масштабирования независимого поиска путей можно использовать неизменяемый
NavMesh и отдельные query contexts для одновременно выполняемых запросов:
[dtNavMeshQuery](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/Detour/Include/DetourNavMeshQuery.h)
содержит изменяемое состояние поиска/node pools. Это проектное предложение,
а не реализованная интеграция. Пакетное steering/avoidance потребует снимка соседей
и пространственного индекса; наивный полный попарный обход ограничит масштаб.

Для первого сценария предлагается строить NavMesh до измеряемого окна. Обновление
NavMesh при динамических препятствиях — отдельная возможная нагрузка. Агенты
должны иметь достижимые цели, реальные препятствия и пересекающиеся потоки;
частоту replanning нужно фиксировать, а не бессмысленно искать тот же путь каждый кадр.

## Предложение, ещё не решение

Начать с Jolt: он уже имеет CPU jobs, backend и контактную stress scene. Перенести
полезные части в Bistro, затем добавить настоящую навигацию её персонажей. Оба вида
симуляции выполняются на CPU, но ни один вариант не гарантирует ускорение или загрузку всех ядер.

Внешняя ручка нагрузки — количество при спавне, по существующему паттерну частиц.
Физические тела и агенты должны масштабироваться независимо. Настройка ноль
отключает соответствующую нагрузку. Нужны проверка значения до выделения памяти
и согласованные ёмкости физических/навигационных структур. Точные имена CVar и
формулу количества выбрать при реализации с учётом уже существующих Count/CVar;
не вводить параллельную систему пресетов.

Агенты получают цели и рассчитывают пути вместо движения по готовым маршрутам;
их обход препятствий и соседей должен распределяться по jobs. Для физики также
предлагается общий scheduler, поскольку исходный вопрос включает полезную работу
на нашей job system. Это требует технического адаптера, а не второго полного пула.
Сложное взаимодействие физических предметов с перестройкой NavMesh не включать
в первый этап без отдельной потребности.

Будущие изменения должны охватить backend/build dependency, мост к JobSystem,
компоненты и синхронизацию тел, порядок обновления App, статические colliders Bistro,
подготовку NavMesh, спавн и обновление персонажей, существующие CVar и тесты.
Навигация должна стать единственным владельцем перемещения соответствующих
персонажей, физика — соответствующих динамических предметов. Старое маршрутное
или летающее движение не должно одновременно перезаписывать их transforms.
Для навигации нужны проверки достижимости, препятствий и толпы; для физики —
контактов, жизненного цикла тел и завершения зависимых jobs на разных размерах пула.

Минимальная будущая проверка:

1. Зафиксировать Release EXE/config, seed, camera, timestep, worker count,
   число активных тел/агентов и частоту поиска пути. Прогреть загрузку и caches.
2. Проверить нагрузки по отдельности и совместно внутри Bistro. Рост количества
   видимых объектов увеличит также GPU skinning, тени и draw work; измерять CPU
   этапы отдельно, чтобы видеть стоимость симуляции в общем кадре.
3. Измерить wall time шага, суммарное CPU time workers, busy/idle и waits,
   frame p50/p95/p99, GPU gaps и отставание симуляции. Текущий benchmark сообщает
   среднее frame time, чего недостаточно для этих выводов.
4. Проверить один поток и несколько размеров пула, а также установившуюся
   нагрузку: тела не должны незаметно уснуть, агенты — все остановиться в тупике.
   При фиксированном шаге отдельно учитывать число реально выполненных ticks.

## Дерево решений интервью

- Согласовано: полезная масштабируемая симуляция для сравнения разных систем.
- Q2 закрыт: только механизм масштабирования количества при спавне; выбор
  пресетов/железа не является частью этой задачи.
- Q3 закрыт: только внутри Bistro.
- Открыто Q4: физика дополнительных предметов, замена полёта исходных предметов
  либо исходные предметы с дополнительными копиями. Вопрос определяет владение
  transform и возможность независимо масштабировать число тел.
- Техническая рекомендация: сначала адаптация Jolt, затем навигация; общий
  scheduler, стабильный шаг и проверки воспроизводимости. Эти детали не требуют
  обсуждения методики оценки пользовательских машин.

ADR пока не создаётся: архитектурный выбор не принят. Документ не разрешает
merge JoltPhysics и не утверждает непроверенный прирост производительности.
