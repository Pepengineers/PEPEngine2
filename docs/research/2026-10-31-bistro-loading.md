# Ускорение загрузки Bistro

Статус: требования согласованы, реализация и измерения выполнены 2026-11-01. Результаты и ограничения приведены в [отчёте](../reports/2026-11-01-bistro-loading.md), решение — в [ADR-0008](../adr/0008-bounded-parallel-scene-loading.md).

## Требование

Пользователь сообщил о долгой загрузке Bistro и предложил параллельное чтение и разбор ресурсов. На целевых системах предполагается быстрый SSD и минимум 16 ГБ RAM. Ограничения CPU пока не заданы.

## Подтверждённые границы

- Измеряется время до полностью готовой сцены; фоновая догрузка после начала отображения не входит в решение. Определение полной готовности Bistro добавлено в CONTEXT.md.
- На этом этапе сохраняется импорт исходных моделей через Assimp при запуске. Запекание ресурсов будет добавляться позднее в редакторе; подготовленный формат и постоянный импорт-кэш в текущую работу не включаются.
- Уточнение по существующему коду: модели импортирует Assimp, текстуры декодирует отдельный TextureLoader через WIC/DirectXTex. Сохранение текущего импорта не требует переноса текстур в Assimp.
- Минимальная целевая RAM — 16 ГБ. Пользователь запросил настраиваемый через CVar размер бюджета загрузки, а не фиксированную константу. Точная область учёта и начальное значение ниже предложены для итогового согласования.

## Факты исходной версии

- Приложение загружает обе части, Exterior и Interior (`Apps/App/src/App.cpp:16–26`), а не только интерьер. Размеры исходных OBJ в рабочей копии: 296,9 и 103,4 МиБ. Размер всех PNG в каталоге сцены — 1293,5 МиБ; это не объём фактически используемых текстур или распакованных пикселей.
- `WorldLoader.cpp:756` обходит OBJ последовательно. Каждый OBJ импортируется через `LoadMesh` (`:658`) и `MeshImporter::ImportSingleMeshAsset` (`MeshImporter.cpp:767`). Предметы внутри OBJ не являются отдельными независимо читаемыми файлами.
- `BuildObjMaterialSlots` последовательно загружает карты материалов; GPU-текстуры переиспользуются по пути и назначению (`WorldLoader.cpp:353–448,577–636`).
- PNG декодируются на CPU, затем строятся mip-уровни (`Engine/Engine.Core/src/IO/TextureLoader.cpp:367–381`). Размер сжатого файла не отражает объём этой работы и расход RAM.
- `Texture::WithType` копирует весь объект, включая массивы пикселей (`Engine/Engine.Core/src/Types/TextureTypes.cpp:29–33`). Этот метод вызывается после генерации mip-уровней (`TextureLoader.cpp:228`) и перед GPU-загрузкой (`WorldLoader.cpp:380`).
- Каждая GPU-текстура отправляется отдельным command list с последующим `Flush` (`Apps/App.Base/src/RenderModule.cpp:333–334`). Это ожидание CPU через fence (`Engine/Engine.RendererDX12/src/GDX12CommandQueue.cpp`, методы `Flush` и `CPUWaitForFenceValue`). Локальный upload-буфер живёт благодаря этому ожиданию: просто удалить `Flush` нельзя.
- `GDX12GeometryBuffer::AddMesh` пересобирает накопленные vertex/index buffers. Для текущей Bistro это происходит при добавлении двух частей, а не каждого предмета (`Engine/Engine.RendererDX12/src/GDX12GeometryBuffer.cpp:185–186`).
- Реестры ресурсов, таблицы RenderModule, распределение дескрипторов и пулы command lists изменяют общие контейнеры без синхронизации. Запустить существующие `AssetManager::LoadTexture` / `RenderModule::CreateTexture` одновременно без изменения владения данными небезопасно.
- Запуск включает инициализацию рендера и компиляцию шейдеров. Её нужно измерять отдельно от импорта сцены (`Apps/App.Base/src/App.cpp:150`, `Engine/Engine.RendererDX12/src/GDX12ShaderCompiler.cpp:94,139`).
- В актуальном дереве есть enkiTS-backed `JobSystem` (`Engine/Engine.Core/Include/Engine.Core/Jobs/JobSystem.h`, `src/Jobs/JobSystem.cpp`) и тесты. `ParallelJob::Schedule` и ожидание незавершённых jobs вызываются в потоке, создавшем пул; объект работы и результаты должны жить до Complete. Владение пулом в приложении пока не обнаружено. Ранний вывод об отсутствии реализации jobs более не актуален.

## Принятый план

1. Измерить Release-запуск: инициализация рендера/шейдеры, импорт каждого OBJ, декодирование и mip-уровни, копирование/упаковка пикселей, GPU upload/wait, создание мира, первый полностью готовый кадр. Разделить первый и повторные запуски; учитывать файловый кэш ОС. Постоянного кэша подготовленных ресурсов в этой версии нет.
2. Устранить ненужные копии пикселей и объединить GPU-загрузки в пакеты. Сохранять upload-ресурсы до завершения fence; ограничить объём незавершённых загрузок.
3. Дедуплицировать запросы текстур до запуска работ. Чтение, декодирование и mip-уровни независимых текстур выполнять ограниченным числом задач с собственными результатами. Реестры, GPU-ресурсы, материалы и ECS публиковать последовательно в согласованном порядке.
4. При подтверждённой цене импорта выполнять два OBJ-импорта независимо с отдельными `Assimp::Importer`. Два файла сами по себе дают только две такие задачи; это не обещание двукратного ускорения всего запуска.
5. Запекание геометрии и текстур с готовыми mip-уровнями оставить будущему редактору согласно выбранным пользователем границам.

Для работ использовать один принадлежащий приложению JobSystem, созданный до загрузки сцены и сохраняемый для последующей логики. Планирование и Complete остаются в потоке-владельце. CPU-работы возвращают результаты в заранее выделенные независимые слоты; они не вызывают общие реестры или рендер. Текстуры обрабатываются ограниченными пакетами, чтобы не держать одновременно все промежуточные изображения и upload-буферы.

Проверка результата: время до согласованной готовности, пиковая RAM, сохранение геометрии, материалов, прозрачности, bounds и поведения при ошибках. Число workers выбирать по замерам, учитывая рост памяти при одновременном импорте.

## Контракт CVar

- `Loading.TransientBudgetMiB` через существующий `AutoConsoleVariable<int>`. Значение по умолчанию — 1024 МиБ. Оно проверено на текущей машине с 32 ГБ RAM; совместимость с физической конфигурацией 16 ГБ отдельно не подтверждена.
- Бюджет ограничивает оценочный объём временных данных одновременно выполняемых загрузочных задач и незавершённых GPU-upload. Это не ограничение всей памяти процесса, постоянных CPU-кэшей или VRAM. Внутренние аллокации Assimp/WIC/DirectXTex не имеют жёсткого ограничения в текущих API; их влияние проверяется по пику памяти процесса.
- Значение считывается один раз в начале загрузки; изменение во время работы применяется к следующей загрузке. Нулевое/отрицательное значение отклоняется с понятной ошибкой, без безлимитного режима; перевод МиБ в байты проверяется на переполнение.
- Ограничение применяется до запуска задач по оценке распакованных данных, а не по сжатому размеру PNG. Если один неделимый ресурс превышает бюджет, он обрабатывается отдельно с диагностикой превышения; очередь не должна ждать недостижимого свободного объёма.
- После загрузки и публикации временные данные освобождаются; upload-буферы сохраняются до соответствующего fence. Уже опубликованные данные существующего CPU-кэша не становятся автоматически освобождаемыми из-за нового бюджета.
- В ходе реализации в рабочем дереве появился общий механизм CVar/INI из параллельной работы. Бюджет подключён к нему: `[ConsoleVariables]` / `Loading.TransientBudgetMiB` в `Config/Engine.ini` рядом с exe; стартовый аргумент `-Loading.TransientBudgetMiB=1024` переопределяет значение из INI до загрузки сцены. Положительное значение проверяет валидатор CVar; отдельная конфигурационная система не добавлялась.

## Итоговое согласование

Пользователь принял предложенный контракт и явно поручил реализацию с замерами времени и пиковой памяти до и после. Реализованы CPU-работы через общий JobSystem, дедупликация текстур, ограничение пакетов, последовательная публикация и пакетный GPU-upload. Дополнительно исправлено преждевременное переиспользование открытого command list и время жизни COM для сохраняемой DirectXTex WIC-фабрики; оба случая покрыты проверками.

При бюджете 1024 МиБ оба OBJ по оценке крупнее бюджета и выполняются по одному; текстуры готовятся параллельно. Отдельный прогон с 8192 МиБ подтвердил одновременный импорт двух OBJ ценой большего пика памяти. Подготовленный формат, потоковая догрузка и изменения качества материалов не добавлялись.
