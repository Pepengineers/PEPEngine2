# Job System: исследование и открытые решения

Дата: 2026-10-31. Статус: исследование и согласование; интеграция не начата.

## Согласованные требования

- Удобство описания и планирования работ по образцу Unity IJob / IJobParallelFor.
- Первоначальный пользовательский API ограничен наследуемыми базовыми классами `Job` и `ParallelJob`. Job выполняет обработку данных системы последовательно, как текущий код; ParallelJob обрабатывает данные пакетами на нескольких потоках. Первоначальное название MainThreadJob заменено пользователем на Job; отдельного типа с закреплением на главном потоке не требуется. IJobEntity-подобный API и автоматическое выведение ECS-запросов в первую версию не входят.
- Сохраняем существующий ECS.
- Системы обрабатывают данные в заданном порядке; внутри одной системы пакеты выполняются параллельно.
- Все пакеты предыдущей системы завершаются до начала обработки следующей.
- Приложение явно задаёт порядок и зависимости в своём Tick/Update и может вставлять собственные работы. SceneManager не строит скрытую цепочку по приоритетам. Автосортировка по метаданным — отдельная будущая задача.
- После уточнения пользователь выбрал сохранение ExecuteIndirect и параллельное обновление ECS/подготовку данных объектов. Отдельный CPU draw-путь не нужен. Это включает пакетное построение исходных indirect-аргументов там, где они действительно создаются или изменяются, а не обязательную параллельную запись DX12 command lists.
- Запись существующих проходов и постобработки остаётся последовательной. Обсуждённое разбиение записи opaque по объектам не входит в первую версию после выбора GPU-driven пути.
- ExecuteIndirect требуется также для теней; текущая реализация для каскадов солнца и point/spot-теней сохраняется и проверяется на движущихся объектах.
- Нужно учитывать повторное использование command list и allocator, существующие кадры в полёте и при необходимости изменить DX12-слой.
- Нагрузка для проверки — движение существующих бутылок, столов и стульев внутри Bistro; дополнительные копии не добавляются. Пользователь подтвердил рекомендованный вариант второго вопроса.

Решение о последовательности систем: [ADR-0001](../adr/0001-sequential-systems-parallel-batches.md). Термины: [CONTEXT.md](../../CONTEXT.md).

## Что переносим из модели Unity

[IJobParallelFor](https://docs.unity.com/en-us/engine/6000.0/script-reference/unity/jobs/ijobparallelfor) описывает независимую обработку индексов и разбиение на пакеты. JobHandle задаёт зависимость или точку ожидания; порядок выполнения отдельных индексов не гарантируется.

[Unity Entities](https://github.com/Unity-Technologies/EntityComponentSystemSamples/blob/master/EntitiesSamples/Docs/entities-jobs.md) добавляет IJobEntity и IJobChunk для обхода ECS. [Автоматическое отслеживание чтения/записи компонентов](https://docs.unity.cn/Packages/com.unity.entities@1.3/manual/systems-scheduling-jobs.html) — отдельная возможность ECS-интеграции. Она не следует автоматически из сходства имён IJob и Schedule и пока не включена в требования.

Согласованная форма API, пока без полного C++-объявления:

- Job::Execute() содержит последовательный обход; выполнение Job синхронное, как в текущем коде.
- ParallelJob::Execute(index) обрабатывает один элемент; Schedule(count, batchSize, dependency) возвращает JobHandle, а разбиение на пакеты выполняет планировщик.
- Пользователь отдельно запросил зависимости по образцу Unity: следующий этап можно поставить в очередь заранее, передав JobHandle предыдущего. Начало обработки следующей системы допускается только после завершения всех пакетов предыдущей.
- Complete завершает CPU-работу. GPU fence отдельно определяет, когда можно повторно использовать allocator и ресурсы кадра.
- Подтверждён контракт времени жизни: C++-объект работы и указанные в нём данные сохраняются до завершения; активный объект нельзя менять, уничтожать или планировать повторно. Schedule на временном объекте запрещён. Для локальной работы Complete вызывается до выхода из области видимости.

[Unity job dependencies](https://docs.unity.com/en-us/engine/6000.0/manual/scripting/programming-distribute-work-threads/job-system/job-dependencies) поддерживают передачу JobHandle в Schedule и объединение нескольких зависимостей. В [enkiTS TaskScheduler.h](https://raw.githubusercontent.com/dougbinks/enkiTS/master/src/TaskScheduler.h) есть ICompletable/Dependency и SetDependency; зависимость определяет готовность работы, но сама по себе не решает владение объектом C++.

Предлагаемый путь кадра после выбора ExecuteIndirect: выбор свободных ресурсов кадра → явно связанная приложением цепочка пакетных обновлений систем → пакетная подготовка матриц, bounds и instance-данных → Complete финального CPU handle → последовательная запись существующих GPU culling/ExecuteIndirect/постпроходов → отправка в GPU-очередь. Исходные indirect-шаблоны подготавливаются при создании/изменении состава сцены, отдельно от обычного движения. Между параллельными системами Complete не требуется. Синхронный Job сначала завершает входную зависимость, затем выполняет Execute в вызывающем потоке.

Это существующая проблема идентичности сущностей; стартовая сцена без удаления и повторного создания её не требует, замена ECS для исправления не нужна.

### DX12

- `Engine/Engine.RendererDX12/src/GDX12CommandList.cpp:13,43`: список уже владеет allocator; Reset сбрасывает оба. Для первой версии можно повторно использовать пары, не вводя отдельный пул allocator.
- `Engine/Engine.RendererDX12/src/GDX12CommandQueue.cpp:46,131`: выданный для записи список сразу попадает в working; повторный запрос может вернуть его как завершённый из-за нулевого или старого fence. Перед параллельной записью необходим отдельный учёт выданных и отправленных списков. Один mutex не исправляет этот жизненный цикл.
- `Engine/Engine.RendererDX12/src/GDX12CommandQueue.cpp:78`: отправка вектора списков под общим fence уже существует; коллекции пула и счётчик fence не синхронизированы.
- `Engine/Engine.RendererDX12/src/GDX12Resource.cpp:8` и `GDX12TextureResource.cpp:21`: вычисление barriers меняет общее состояние ресурсов во время записи. Если workers сами вызывают эти helpers, возникает гонка. Для уточнённой схемы helpers остаются у координатора прохода, а workers записывают только draw/bind-команды без изменения состояний ресурсов; локальный tracker каждого command list не является обязательным.
- `Engine/Engine.RendererDX12/src/GDX12DescriptorHeap.cpp:49`: распределение descriptors изменяет общий контейнер. Создание/изменение ресурсов и descriptors следует отделить от параллельной записи.
- `Engine/Engine.RendererDX12/Include/Engine.RendererDX12/GDX12UploadBuffer.h:178,202`: CopyData пишет в отображённую память; разные стабильные диапазоны можно разделить между задачами. Resize одновременно с такими задачами недопустим.

[Microsoft D3D12Multithreading](https://learn.microsoft.com/en-us/samples/microsoft/directx-graphics-samples/d3d12-multithreading-sample-win32/) — готовый пример параллельной записи отдельных списков. [Документация allocator/list](https://learn.microsoft.com/en-us/windows/win32/direct3d12/recording-command-lists-and-bundles) описывает ограничения владения, повторного использования и fence. Предлагаемый простой вариант для обсуждения: координатор выдаёт отдельные пары list/allocator, workers записывают их эксклюзивно, координатор отправляет в заранее определённом порядке и возвращает пары в пул после завершения GPU.

### Enhanced Barriers: уточнение варианта RHI

Пользователь предложил рассмотреть Enhanced Barriers. Для обновляемого RHI это подходящий кандидат: отдельно задаются синхронизация GPU-работ, доступ к памяти и layout текстур; для буферов layout отсутствует. Есть Texture, Buffer и Global barriers. Основание: [объяснение Microsoft](https://devblogs.microsoft.com/directx/d3d12-enhanced-barriers-preview/).

В коде уже есть GDX12CommandList::EnhancedTextureBarrier (`src/GDX12CommandList.cpp:290`) и helpers GDX12TextureResource (`src/GDX12TextureResource.cpp:21`), но проходы их не используют. Helpers меняют общие Sync/Access/Layout при записи и небезопасны при параллельном вызове workers. В уточнённой пользователем схеме переходами владеет координатор прохода, поэтому вызов этих helpers из workers не нужен. Поддержку Buffer/Global barriers следует учитывать при выборе Enhanced-пути.

Предлагаемый контракт после уточнения: координатор записывает переходы и однократную очистку до geometry command lists, workers записывают draw/bind-команды для непересекающихся пакетов объектов в фиксированных состояниях ресурсов, затем координатор записывает переходы к следующему последовательному проходу. Layout сохраняется между отправками, а Sync/Access учитывают границы ExecuteCommandLists. Совместимость с legacy uploads и SDK требует явных границ через COMMON; смешивание моделей на одном subresource может иметь стоимость. Основание: [DirectX Enhanced Barriers spec](https://microsoft.github.io/DirectX-Specs/d3d/D3D12EnhancedBarriers.html). Общий локальный tracker с разрешением начальных состояний при отправке нужен только при дальнейшем расширении на независимо записываемые переходы; он исключён из минимальных обязательных изменений.

Общие RT/depth остаются GPU-выходами прохода; параллельная CPU-запись в разные command lists не означает одновременного изменения их CPU-метаданных. Каждый direct list самостоятельно устанавливает PSO, root signature, descriptors, viewport и render targets: состояние предыдущего direct list не наследуется. См. [Microsoft pipeline state](https://learn.microsoft.com/en-us/windows/win32/direct3d12/managing-graphics-pipeline-state-in-direct3d-12). Пара list/allocator эксклюзивна на запись и возвращается после fence; проверка жизненного цикла пула остаётся обязательной.

Граница решена пользователем: сохраняем текущий GPU-driven ExecuteIndirect и не добавляем CPU draw-путь. Параллелизуется CPU-подготовка данных и исходных аргументов, а не разбиение компактного GPU indirect-потока на CPU draw-вызовы. После этого выбора локальный per-list tracker не входит в обязательный объём первой версии. Enhanced Barriers остаются отдельным возможным улучшением RHI, не условием пакетного обновления данных.

### Исходные indirect-аргументы и тени

[Microsoft Indirect Drawing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/indirect-drawing) различает command signature — формат записи — и argument buffer с конкретными параметрами draw. Буфер может заполняться CPU или GPU. В нашем пути исходные кандидаты подготавливаются на CPU независимо от последующей видимости; GPU строит компактные списки для камеры и источников света.

`Apps/App.Base/Include/App.Base/Systems/GPUDataUpdateSystem.h:176` последовательно заполняет GDX12IndirectDrawArgs по submeshes; фиксированные `_CBufferIndices` уже задают непересекающиеся выходные слоты. Для этого подходит ParallelJob по пакетам сущностей с сохранением внутреннего обхода частей одного объекта, без общего push_back или счётчика добавления.

`GDX12IndirectDrawArgs` (`GDX12ConstantStructures.h:120`) хранит ID экземпляра, количества и смещения индексов/вершин. Матриц и bounds в записи нет. Обычное движение не требует её перестроения; изменяющиеся матрицы и bounds обновляются в ресурсах текущего кадра.

`GDX12DeviceResources.cpp:50` создаёт один общий upload IndirectCommandsCache на устройство вне FrameConstants. Его нельзя перезаписывать при обычном движении, пока предыдущие кадры могут читать его. Минимальный путь для фиксированной нагрузки — пакетно построить шаблоны до первой отправки и сохранять их неизменными; изменение состава сцены происходит на безопасной границе. Если в будущем потребуется менять сами аргументы каждый кадр, нужны отдельные fenced frame slots и переключение всех culling-потребителей на них.

Поэтому исправление dirty/bounds должно отделить изменение transform от изменения геометрии/исходных draw-шаблонов. Простое выставление renderer.DirtyFlag при каждом движении небезопасно: существующая ветка одновременно перезаписывает общий IndirectCommandsCache.

В текущем рабочем дереве каскады солнца уже выполняют GPU-culling общего набора кандидатов и ExecuteIndirect для каждого каскада (`GDX12CascadedShadowPass.h:135,162`); point/spot-проход делает GPU-culling и ExecuteIndirect для каждого теневого вида (`GDX12LocalShadowPass.h:110,132`). Видимость теней не должна ограничиваться списком видимых камерой объектов. Для летающих предметов проверяется корректность bounds и политика обновления/кэширования shadow maps.

Уточнение динамических теней: cached-проверки солнца и локальных источников сейчас не отслеживают движение shadow casters; локальные LightComponent по умолчанию Cached. Источник уже имеет InvalidateShadow, но production-вызовов при движении caster не найдено. Для воспроизводимой сцены с постоянно летающими предметами минимальная рекомендуемая политика — EveryFrame для затронутых теневых источников. Это обеспечивает обновление теней без новой системы пространственной инвалидизации. Общий механизм точной инвалидизации кэшированных теней за пределами этой сцены отдельно не реализуется в первой версии.

Поддержка драйвером опциональна: перед использованием Barrier проверяется D3D12_FEATURE_D3D12_OPTIONS12.EnhancedBarriersSupported, независимо от номера интерфейса command list. См. [Microsoft OPTIONS12](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_feature_data_d3d12_options12). Поддержка на фактических адаптерах запуском пока не проверена.

Открытое решение: Enhanced Barriers становятся обязательным требованием нового пути либо нужен legacy fallback для неподдерживаемых устройств. Рекомендация для текущего бенчмарк-движка — один Enhanced-путь с проверкой поддержки и понятной ошибкой при её отсутствии, без дублирования RHI. Это пока предложение, не принятое решение. Enhanced Barriers не заменяют CPU JobHandle и GPU fence жизненного цикла allocator.

## Проверка полезности

`Apps/App/README.md:13` описывает статическую Bistro без движущейся бенчмарк-нагрузки. Обычный opaque-проход уже использует ExecuteIndirect (`GDX12OpaquePass.h:173`), поэтому количество сущностей не равно количеству CPU draw calls. Ускорение обновления ECS и ускорение записи команд нужно измерять отдельно; загрузка всех ядер сама по себе не критерий успеха.

Для выбранного пользователем сценария важно: `Apps/App.Base/src/ECS/WorldLoader.cpp:647,679` создаёт одну renderable ECS-сущность на весь OBJ. Interior пока не состоит из отдельных ECS-бутылок/столов/стульев. В исходном `Assets/Scenes/Amazon Lumberyard Bistro/Interior/interior.obj` есть именованные группы бутылок, столов и стульев; количество групп нельзя автоматически считать числом целых предметов с учётом частей и материалов. Для независимого движения нужно сохранить принадлежность геометрических частей предмету и выделить ему собственную трансформацию, сохранив материалы и bounds. Это изменение пути загрузки сцены; замена ECS не требуется.

Предлагаемые проверки после согласования реализации: сравнить состояние ECS с однопоточным эталоном; проверить покрытие диапазонов без повторов и пропусков; проверить зависимость A → B на нескольких workers; проверить два запроса command list до отправки и возврат только после fence; выполнить DX12 debug-layer smoke и замеры CPU-этапов на одинаковой нагрузке.

## Решения первого раунда

Пользователь выбрал два наследуемых базовых класса Job и ParallelJob, сохранение текущего ECS и движение существующих бутылок, столов и стульев внутри Bistro. Job означает последовательную обработку данных системы, ParallelJob — параллельную пакетную обработку. Порядок систем с параллельными пакетами подтверждён отдельно в ADR-0001.

## Решения второго раунда

MainThreadJob переименован в Job с последовательной обработкой. Для Bistro подтверждено движение исходных предметов, а не создание дополнительных копий.

## Решения третьего раунда

Подтверждены Job::Execute(), ParallelJob::Execute(index), запуск ParallelJob через Schedule с возвращаемым JobHandle и Complete, а также enkiTS. Пользователь расширил контракт: нужны зависимости через JobHandle для связывания систем, без обязательного Complete после каждой параллельной системы. Строгий порядок обработки систем сохраняется зависимостями.

## Решения четвёртого раунда

Подтверждено сохранение объектов работ до завершения. Пользователь выбрал ручное построение порядка в приложении Tick/Update, включая вставку собственных jobs, вместо рекомендованной автоматической цепочки SceneManager. Автосортировка по метаданным отложена. Основание зафиксировано в [ADR-0002](../adr/0002-application-owned-update-order.md).

## Решение о GPU-driven пути

Пользователь подтвердил сохранение ExecuteIndirect, отсутствие отдельного CPU draw-пути и параллельное обновление ECS/подготовку данных объектов. Отдельно запросил ExecuteIndirect для теней и пакетное заполнение CPU indirect-аргументов. Текущая реализация уже использует исходные CPU-шаблоны и GPU-отбор, включая тени; первая версия переносит подготовку данных в jobs и сохраняет этот путь. Основание: [ADR-0003](../adr/0003-indirect-rendering-parallel-object-preparation.md).

## Предложение к реализации для окончательного согласования

- Переносим существующий порядок систем в явный код приложения; синхронные системы совместимы с асинхронной цепочкой через ожидание входной зависимости. Никакой неявной сортировки или второго запуска в SceneManager.
- Пустой JobHandle означает отсутствие ожидания; Complete можно вызывать повторно. CombineDependencies объединяет завершение нескольких jobs. Зависимости задаются handles ранее запланированных работ; повторный Schedule активного объекта запрещён.
- Объекты и компоненты создаются до выполнения задач; добавление/удаление сущностей, смена сцены, изменение размеров GPU-буферов происходят после завершения использующих их работ. Полный механизм отложенных ECS-команд не входит в первую версию.
- Один пул enkiTS обслуживает логику и подготовку данных объектов. Количество workers выбирается автоматически; для проверок нужен режим одного потока. Размер пакета передаётся явно и подбирается по замерам.
- Ошибки задач не должны приводить к зависшим зависимостям: они сообщаются вызывающему потоку через Complete; кадр с неуспешной подготовкой не отправляется в GPU-очередь.
- Сохраняем ExecuteIndirect и GPU-culling для opaque и теней. Шаблоны draw-команд строятся пакетно при изменении состава сцены, а динамические матрицы/bounds/instance-данные обновляются пакетно каждый кадр. См. [ADR-0003](../adr/0003-indirect-rendering-parallel-object-preparation.md).
- Запись DX12-проходов остаётся последовательной; workers не получают command lists и не вызывают mutable barrier helpers. Жизненный цикл существующего пула учитывается, но отдельная переработка для многопоточной записи и общий per-list tracker не обязательны для выбранного объёма.
- Вопрос миграции на Enhanced Barriers отделён от внедрения Jobs: выбор основного или fallback-пути ещё не подтверждён и не блокирует пакетную подготовку объектов.
- Движение существующих предметов Bistro воспроизводимо, без физики; предмет сохраняет все material sections и корректный pivot. Исправляется инвалидирование bounds.
- Проверки: эквивалентность последовательного и пакетного обновления, покрытие индексов, зависимости и ошибки задач, lifetime пула до/после fence, DX12 debug-layer smoke. Замеры обновления ECS и записи команд выполняются отдельно на одной нагрузке; заранее заданное ускорение не обещается.

Подтверждённые требования перечислены отдельно выше; низкоуровневые детали этого раздела предложены для проверки итогового понимания. Перед изменением кода требуется итоговое подтверждение по вызванному grilling workflow; отдельные новые раунды нужны только при выявлении существенной неоднозначности.
