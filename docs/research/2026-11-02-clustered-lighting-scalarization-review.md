# Проверка архитектуры clustered lighting по первоисточникам

Дата: 2026-11-02. Исследование; код рендера в этой проверке не менялся.

## Сетка фрустума и использование глубины

Регулярная сетка фрустума не требует depth buffer для построения границ ячеек.
В статье Olsson, Billeter, Assarsson **Clustered Deferred and Forward Shading**
(HPG 2012), §3.1, пространство разбивается на экранные XY-тайлы и экспоненциальные
интервалы view-space Z. Формула ключа ячейки использует XY пикселя и его Z.
Прототип статьи дополнительно выделяет занятые кластеры из G-buffer; §3.2
рассматривает как неявные границы сетки, так и более тесные границы по реальным
samples. Поэтому нельзя приписывать всей технике требование min/max depth, но
нельзя и утверждать, что исходный GPU-прототип обходился без данных глубины:
его forward-вариант в §4 использовал pre-Z.
[Статья авторов](https://www.cse.chalmers.se/~uffe/clustered_shading_preprint.pdf),
[доступный полный текст опубликованной работы](https://www.researchgate.net/publication/289301155_Clustered_deferred_and_forward_shading).

Следует различать три операции: построение пространственной сетки; необязательное
исключение пустых ячеек по depth buffer; определение ячейки конкретного пикселя
по его глубине/позиции. Первую можно выполнять без геометрии сцены. Последняя
в deferred по-прежнему использует G-buffer depth, чтобы выбрать правильный Z-слой.
Это вывод из формулы cluster key в §3.1 указанной статьи.

## CPU-построение списков — существующий production-подход

Emil Persson в **Practical Clustered Shading**, SIGGRAPH 2013, слайд 12, описывает
реализацию Avalanche: пространственная сетка 64×64 пикселя × 16 Z-слоёв,
CPU light assignment и неявные, независимые от сцены границы. Слайды 13 и 16–17
показывают экспоненциальные интервалы и компактные списки offset/count/indices.
В слайдах о culling обход организован вокруг источника: его объём последовательно
сужается по Z/Y/X, после чего индекс попадает в пересекаемые ячейки.
[Авторский PDF](https://www.humus.name/Articles/PracticalClusteredShading.pdf),
[страница автора о докладе](https://www.humus.name/index.php?ID=7&page=Articles).

Filament независимо описывает оба пути. Геометрию froxel-сетки можно сохранять,
пока не меняется projection matrix. GPU-вариант проверяет источники для каждого
froxel; CPU-вариант растеризует каждый источник в пересекаемые froxels и может
сразу формировать упакованные списки. Это прямая поддержка предложенной пользователем
архитектуры, а не предположение о невозможности CPU-реализации.
[Документация Filament, Clustered Forward Rendering / Implementation notes](https://google.github.io/filament/Filament.md.html).

Источник нужно добавлять во **все** ячейки, пересечённые его объёмом влияния.
Одной ячейки, содержащей центр, недостаточно: сфера point light или конус spot
light обычно пересекают несколько ячеек. Простая проверка bounding sphere
консервативна для spot, но добавляет лишние кандидаты; более тесное cone culling
является отдельной оптимизацией. Первые два предложения следуют из light-volume
assignment в Avalanche и Filament; необходимость тесного spot culling отдельно
разбирает [Bart Wronski, Cull that cone!](https://bartwronski.com/2017/04/13/cull-that-cone/).

## Что было сделано до CPU-переделки

На момент этой исследовательской проверки `DeferredLighting.hlsl` строил 32 логарифмических Z-слоя отдельно для
каждого тайла 16×16, подгоняя их под MinDepth/MaxDepth. OccupiedSlices отсекает
пустые слои, а построение масок и shading объединены в одном dispatch. Это
трёхмерная кластеризация, но её сетка зависит от видимой глубины каждого тайла.
Она не реализует предложенную общую сетку с заранее построенными списками.
Путь с wave intrinsics объединяет маски по wave и передаёт единый light index
через WaveReadLaneFirst; сам принцип скаляризации здесь присутствует.
Основание: `Engine/Engine.RendererDX12/Shaders/DeferredLighting.hlsl`,
`GDX12DeferredLightingPass.h` и `docs/rendering/clustered-lighting.md`.

## Вывод для следующего изменения

Для описанного пользователем варианта целесообразно отделить общую неявную
сетку от light assignment и shading. При текущих 135 светильниках Bistro
(124 point + 11 spot, `Apps/App/README.md`) CPU light-centric assignment является
обоснованным кандидатом для измерения. Его превосходство над GPU **не измерено**.
CPU-путь должен учитывать перестроение списков при движении камеры/света,
стоимость загрузки буферов и согласованность cluster lookup с проекцией.

Размер сетки нельзя переносить из текущего shader без оценки: для 1920×1080,
16×16×32 получается 261120 ячеек. Полная маска на 135 источников занимает
5 uint на ячейку, всего 5222400 байт (около 4.98 MiB), ещё до прочих данных.
Это арифметическая оценка, не замер нагрузки. Компактные списки или более крупные
XY-тайлы уменьшают эту цену, но изменяют стоимость traversal и точность culling.

## Статьи о скаляризации и CoD

Прочитаны обе части Francesco Cifariello Ciardi: [Part 1](https://flashypixels.wordpress.com/2018/11/10/intro-to-gpu-scalarization-part-1/)
и [Part 2 — Scalarize all the lights](https://flashypixels.wordpress.com/2018/11/10/intro-to-gpu-scalarization-part-2-scalarize-all-the-lights/),
включая примечания. Первая объясняет uniform/varying данные и GCN scalar/vector
пути. Вторая различает обход по ячейкам и по отдельным источникам: общий источник
в соседних ячейках выгодно обрабатывать одной wave-итерацией. Для отсортированных
списков показан выбор следующего общего ID через WaveActiveMin; предусмотрен
быстрый путь, когда все активные lanes обращаются к одной ячейке. Примечание о
helper lanes важно при переносе такого цикла в pixel shader; текущий проход — CS.

В [докладе Michal Drobot, SIGGRAPH 2017](https://www.realtimerendering.com/advances/s2017/2017_Sig_Improved_Culling_final.pdf)
прочитаны разделы о сетке, скаляризации и Z-binning. Страница 6 прямо допускает
cluster culling без depth pre-pass. Страница 17 объединяет flat bitmask по wave
через OR и обходит установленные биты единым entity index. Текущий код использует
тот же принцип, но биты адресуют локальный список тайла, создаваемый в этом же
dispatch. Это не равнозначно готовой общей сетке.

Страницы 29–33 описывают ещё один вариант: 2D light bitmasks плюс независимые
Z-bins. CPU сортирует источники по Z и строит LUT минимального/максимального ID
для Z-интервалов; GPU сужает диапазон слов и объединяет маски по wave. Поэтому
полная XYZ-сетка и именно этот CoD-подход — разные кандидаты, хотя оба совместимы
с per-light scalarization. Номера страниц здесь отсчитываются с 1 в PDF.

Uniform light index позволяет унифицировать адреса и данные источника. Позиция,
нормаль, BRDF, затухание и shadow lookup конкретного пикселя остаются varying.
Слова SGPR/SALU/SMEM в статье относятся к GCN; реальный ISA, регистры и выигрыш
на другом GPU требуют отдельной проверки, их не доказывает наличие intrinsics.

В этой проверке не выполнялись CPU/GPU-бенчмарки альтернативной архитектуры и
не менялся код рендера. Ранее полученные 9% относятся только к прежнему
синтетическому сравнению tiled и depth-adaptive fused проходов.

Доступ к источникам: полный текст работы 2012 прочитан в её воспроизведении
на ResearchGate; прямой Chalmers PDF вернул 403. Прямое получение PDF Persson
завершалось таймаутом: использованы индексированные фрагменты авторского PDF
и текст слайдов. Раздел Filament о CPU/GPU assignment прочитан полностью
на сайте проекта; это наиболее непосредственно проверенное подтверждение CPU-пути.
