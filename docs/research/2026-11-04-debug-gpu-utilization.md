# Bistro Debug: почему GPU загружен примерно на 40–50%

Дата: 2026-11-04. Исследована существующая Debug-сборка, которую пользователь
запускал из Rider. Код рендера не изменён.

## Вывод

В воспроизведённом сценарии GPU ждёт основной CPU-поток. Самый дорогой участок —
запись команд локальных теней и их проверка D3D12 Debug Layer. Это подтверждено
одновременно CPU-маркерами, полной выборкой стеков и промежутками между пакетами
команд на GPU. Одна только низкая общая загрузка CPU в диспетчере задач этого
не исключает: основной поток занимает почти одно логическое ядро.

В PIX графическая очередь приложения исполняет пакет медианно **26,632 мс**,
затем простаивает до следующего пакета медианно **37,652 мс**. За окно
1000–2000 мс суммарная длительность оболочек пакетов составляет **412,675 мс**,
или **41,27%** окна. Это соответствует порядку величины наблюдаемых пользователем
48%. Оболочка включает промежутки между командами внутри пакета; это не точный
счётчик GR Engine Active и не загрузка GPU всеми процессами компьютера.

## GPU: обычные частоты и отдельно Nsight

Из PIX извлечено **39016 work items без truncation** для графической очереди
3, parallel level 0, окно 1000–2000 мс. Границы пакетов сгруппированы по
`executionId` и `commandListIndex`; неполная последняя группа исключена из
медианы длительностей. Получены 15 полных пакетов и один частичный.
Источник: `gpu-work-1s.json`, расчёт: `gpu-gap-summary.json`.

Nsight по умолчанию **фиксирует GPC на 900 МГц и принудительно отключает VSync**.
Поэтому его трасса меняет баланс CPU/GPU и скрывает простой, наблюдаемый при
обычных частотах. Эти значения нельзя выдавать за обычный FPS или за отсутствие
проблемы в Debug.

| Метрика Nsight | Debug | Исходный Release |
| --- | ---: | ---: |
| Окно, 12 кадров, мс | 543,302 | 534,141 |
| Среднее время кадра, мс | 45,275 | 44,512 |
| GR Engine Active | 96,90% | 97,32% |
| SM Throughput | 23,15% | 24,01% |
| VRAM Throughput | 25,37% | 25,64% |
| PCIe Throughput | 6,20% | 6,52% |
| GPC, МГц | 900 | 900 |

В Debug GPU-маркеры дают средние: local shadows **17,634 мс**,
sun shadows **8,148 мс**, fluid surface **2,565 мс**, particles **3,301 мс**.
Шейдерная occupancy и GR Engine Active — разные показатели; низкую occupancy
нельзя подменять объяснением простоя между CPU submissions.

Обе Nsight-трассы не имеют предупреждений об overflow. Предупреждение о
пропавших per-shader metrics не относится к использованным whole-trace counters.
Time Every Action выключен: точные per-draw выводы здесь не делаются.
В обычном Release CPU/GPU PIX-маркеры не компилировались; его Nsight timing и
счётчики доступны, детализация проходов отсутствует.

## Контрольные запуски без GPU-профайлера

Использован встроенный benchmark, 601 кадр: первый кадр и начальная готовность
отделяются, затем усредняются 600 кадров и завершающее ожидание GPU.

| Запуск | Средний кадр, мс | Эквивалент FPS |
| --- | ---: | ---: |
| Debug, исходные настройки | **65,693** | 15,22 |
| Тот же Debug, `App.Grass.CastShadows=false` через runtime INI | 64,764 | 15,44 |
| Доступный Release | 28,246 | 35,40 |

Отключение только теней травы не устранило ограничение: в этих одиночных
запусках разница всего около 1,4%. Это диагностический эксперимент, не изменение
настроек пользователя и не доказательство ускорения. INI восстановлен в `finally`,
его SHA-256 совпадает с сохранённым оригиналом. Основной путь локальных теней
и debug validation остаётся дорогим и без травы.

**Ограничение Release-контроля:** параллельная работа обновила Release EXE
в 14:54:14 MSK, после первой Nsight-трассы и до benchmark. Поэтому 28,246 мс
характеризуют доступную Release-сборку, а не строгое A/B одного source snapshot.
Начальный Release SHA-256: `5740CE19763DEC89AD509EDCB81FC4635B2EA1535ECFD1F103FA8C2FF76985DF`;
поздний: `95425AFA0B5F97DFA6263C8525E21288022DF1577E98114EDFEE9A41556E93E1`.
Основной вывод опирается на неизменный Debug EXE и его PIX CPU/GPU timeline.

## Где исправлять

- [Включение debug layer](../../Apps/App.Base/src/RenderModule.cpp):
  `RenderModule::Initialize` включает его для DEBUG/_DEBUG. Для замера игровой
  производительности использовать Release; отключать проверки постоянно в Debug
  ради красивой загрузки GPU не требуется.
- [Локальные тени](../../Engine/Engine.RendererDX12/Include/Engine.RendererDX12/RenderPasses/GDX12LocalShadowPass.h):
  для каждой dirty face выполняются copy → clear → cull → draw. Копирование
  переводит **весь массив** shadow maps в COPY_DEST, draw — обратно в DEPTH_WRITE.
  Это повторяет transitions и их validation для каждой face.
- [Отслеживание состояний](../../Engine/Engine.RendererDX12/src/GDX12Resource.cpp):
  текущие helpers создают whole-resource barriers. Основной кандидат на отдельное
  исправление — группировать копирование dirty faces и переходы массива, либо
  корректно отслеживать состояния отдельных slices. Эффект пока не измерен.
- [Трава](../../Engine/Engine.RendererDX12/src/GDX12GrassRenderer.cpp): expansion
  и draw вызываются из каждой грани локальной тени. Это дополнительный CPU/GPU
  расход, но контроль не подтвердил, что одно его отключение решает проблему.

## Границы проверки

- Не установлен исторический commit, после которого загрузка упала с 100%:
  сопоставимого старого Debug-трейса нет. Прежние исследования были в Release.
- Тепловая причина не доказана. `nvidia-smi` выдал невозможные значения мощности,
  Windows formatted GPU counter также вернул значение выше 100%; эти данные
  исключены. Температура на скриншоте сама по себе не устанавливает throttling.
- Начальный PIX launch-capture попал в инициализацию/первый кадр и не использован
  для steady-state выводов. CLI `-App.Grass.CastShadows=0` приложением не
  разбирается: соответствующий ранний эксперимент также исключён. Настоящий
  контроль выполнен через INI и сохранён как `debug-no-grass-valid.json`.
- Отдельный Rust-анализатор не поддержал WRPV v11; native Nsight MCP оборвал
  соединение на большом запросе. Данные успешно прочитаны новым локальным
  соединением native GTAPI, страницами по 500 markers.
- Во время работы в основном checkout начался посторонний merge с конфликтами.
  Его исходники/индекс не исправлялись; сборка движка в рамках этой диагностики
  не выполнялась. Оптимизация рендера и её визуальная проверка не проводились.
