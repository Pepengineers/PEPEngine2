# MGPU для Cloud Picture в Bistro

Рабочий план для `App`. Первой переносим генерацию облаков для картины на стене. По выбору пользователя начинаем с обмена из `MGPU-Noise`: дополнительный адаптер копирует рассчитанные облака в общую память, основной копирует из неё в свою текстуру для показа. Каждый следующий вариант синхронизации обсуждаем и реализуем отдельным шагом.

## Что переносим

В PEPEngine2 на `8e291b95` проект [App](../../PEPEngine2.sln) использует [BistroRenderPipeline](../../Apps/App/src/Rendering/BistroRenderPipeline.cpp). [CloudPictureTexture](../../Apps/App/src/Techniques/CloudPictureTexture.cpp) передаёт в [CloudPictureNoise](../../Engine/Engine.RendererDX12/Shaders/CloudPictureNoise.hlsl) 96 байт констант и записывает одну RGBA8-текстуру одним dispatch. Размер по умолчанию 1024 × 512, полезный объём одного изображения 2 МиБ. Время анимации приходит с CPU. Глубина, G-buffer и результат прошлого кадра шейдеру не нужны. У AO потребовалась бы ещё передача входов сцены.

GPU0 здесь означает основной адаптер приложения, GPU1 — выбранный дополнительный. Первым обычным читателем исходной текстуры на GPU0 служит [UI cloud texture raster](../../Apps/App/src/Techniques/UI/ScenePostUI.cpp). Он рисует в отдельную текстуру постера, которую затем читают сцена и отражения. Инспектор `Environment.CloudPicture` умеет читать сами облака. Такое разделение позволяет оставить UI, материалы и Present на GPU0.

Частота копирования задаёт ещё одно наблюдаемое различие. При отсутствии новых облаков GPU0 может снова скопировать прежнюю публикацию из shared либо пропустить импорт и повторно показать локальную копию. Изображение совпадёт, трафик будет различным. В первом этапе нужен именно обмен через shared с копированием на каждой итерации показа после начального заполнения.

У этих вариантов общие механизмы DX12. Очередь может ждать конкретного значения shared fence на GPU. CPU может проверить завершение без блокировки либо дождаться освобождения ресурса перед его повторным использованием. В `MGPU-IMGUI/HybridUIApp.cpp`, строки 244–275, сигналы в двух направлениях обозначают «экспорт готов» и «импорт закончился, память можно перезаписать». Там же независимая часть сцены отправляется до ожидания UI. Выбор DIRECT/COMPUTE/COPY, количество слотов и чтение напрямую из shared влияют на реализацию и стоимость обмена. В Upscale, с. 4, авторы объясняют выбор локальной копии у потребителя. [DX12 shared heaps](https://learn.microsoft.com/en-us/windows/win32/direct3d12/shared-heaps) · [Синхронизация очередей DX12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/user-mode-heap-synchronization).

## Первый перенос

1. **Подключить адаптер.** Добавить явный выбор GPU для Cloud Picture в [SceneCloudPicture](../../Apps/App/src/Techniques/SceneCloudPicture.cpp). Штатная конфигурация продолжает генерировать облака локально. Для удалённой выбрать устройство по фактическому DXGI-адаптеру и сверить LUID. При невозможности открыть пару сообщить причину. Существующий `App.Async.CloudPicture` управляет локальной очередью.
2. **Привязать вычисление к GPU1.** Использовать тот же shader, размеры, SpeedScale и снимок времени. Создать локальные для GPU1 UAV, descriptors и PSO. Подключить два [Executor](../../Apps/App/src/Graph/RenderGraphExecutor.h) к одному [QueueSubmission](../../Apps/App/src/Graph/QueueSubmission.h). Граф каждого устройства описывает только его объекты. На первый проход достаточно отправлять вычисление и экспорт по порядку на одной очереди GPU1.
3. **Передать изображение.** GPU1 пишет локальную UAV-текстуру и копирует её в ресурс общей кучи. GPU0 импортирует в свою sampleable-текстуру. Обе стороны открывают собственные D3D12-объекты для одной области памяти. Вариант с размещённым общим буфером использует `GetCopyableFootprints` и две `CopyTextureRegion`; шаг строки и объём брать из footprint. Это позволяет сохранить текущий формат и произвольные разрешённые размеры. Исторический пример такого переноса — `git show e8bba652:Apps/App/src/Techniques/CloudPictureTexture.cpp`. Активный маршрут был удалён в `8e291b95`.
4. **Подключить импорт к графу GPU0.** Выбранную локальную текстуру передать в существующий `PrepareMaterials` и инспектор. Объявить запись импорта и чтение той же текстуры в графе. Если выбранный режим требует ожидания удалённого экспорта, передать выданный `CompletionToken` через `PacketWait` пакету импорта. Геометрия без зависимости от облаков может выполняться раньше.
5. **Определить время жизни ресурсов.** Для целой публикации различать три момента: GPU1 закончил экспорт локального источника, GPU0 закончил чтение общей области при импорте, все читатели локального изображения GPU0 закончили работу. Перед заменой разрешения или устройств завершить использующие старые ресурсы submissions на обеих сторонах. Учитывать уже отправленные пакеты и при частичной ошибке. Проверить начальное заполнение до первого показа. Конкретное правило выбора общей области и её повторного использования зависит от решения ниже.
6. **Принять один режим.** Release-сборка и один короткий обычный smoke на двух разных аппаратных адаптерах. В логе различимы устройства и работа экспорта/импорта, на стене Bistro видны движущиеся облака, кадр выводится без явных ошибок. Один GPU подтверждает только локальный путь. Следующий вариант синхронизации — отдельное изменение после приёмки этого.

### Открытое решение первого этапа

Если GPU1 ещё пишет новое изображение, возможны три разных требования к безусловному импорту GPU0: ждать именно текущий экспорт (как в Noise V2), снова копировать последнюю целую публикацию из защищённого слота или экспериментально читать ту же область одновременно с записью. В последнем случае DX12 не гарантирует определённое содержимое. Это решение определяет схему владения памятью, число необходимых слотов и место ожиданий.
