# MGPU для Cloud Picture в Bistro

Согласованный план для `App`. Первой переносим генерацию облаков для картины на стене. Используем путь данных из `MGPU-Noise`. Дополнительный адаптер копирует рассчитанные облака в общую память, основной копирует из неё в свою текстуру для показа. Каждый следующий вариант синхронизации обсуждаем и реализуем отдельным шагом.

## Что переносим

В PEPEngine2 на `8e291b95` проект [App](../../PEPEngine2.sln) использует [BistroRenderPipeline](../../Apps/App/src/Rendering/BistroRenderPipeline.cpp). [CloudPictureTexture](../../Apps/App/src/Techniques/CloudPictureTexture.cpp) передаёт в [CloudPictureNoise](../../Engine/Engine.RendererDX12/Shaders/CloudPictureNoise.hlsl) 96 байт констант и записывает одну RGBA8-текстуру одним dispatch. Размер по умолчанию 1024 × 512, полезный объём одного изображения 2 МиБ. Время анимации приходит с CPU. Глубина, G-buffer и результат прошлого кадра шейдеру не нужны. У AO потребовалась бы ещё передача входов сцены.

GPU0 здесь означает основной адаптер приложения, GPU1 — выбранный дополнительный. Первым обычным читателем исходной текстуры на GPU0 служит [UI cloud texture raster](../../Apps/App/src/Techniques/UI/ScenePostUI.cpp). Он рисует в отдельную текстуру постера, которую затем читают сцена и отражения. Инспектор `Environment.CloudPicture` умеет читать сами облака. Такое разделение позволяет оставить UI, материалы и Present на GPU0.

**Выбор первого этапа.** После начального заполнения GPU0 в каждом кадре импортирует последнюю целую версию, готовую к моменту выбора. Если номер версии прежний, GPU0 снова выполняет копирование из общей памяти. GPU1 запускает следующий расчёт сразу после завершения предыдущего расчёта и экспорта, когда есть свободный слот. У каждого адаптера свой счётчик. В Noise одна ветка показывает безусловную копию, другая — проверку готовности, обе вызываются из основного `Draw`. Независимый темп взят из модели статьи об AA.

У этих вариантов общие механизмы DX12. Очередь может ждать конкретного значения shared fence на GPU. CPU может проверить завершение без блокировки либо дождаться освобождения ресурса перед его повторным использованием. В `MGPU-IMGUI/HybridUIApp.cpp`, строки 244–275, сигналы в двух направлениях обозначают «экспорт готов» и «импорт закончился, память можно перезаписать». Там же независимая часть сцены отправляется до ожидания UI. Выбор DIRECT/COMPUTE/COPY, количество слотов и чтение напрямую из shared влияют на реализацию и стоимость обмена. В Upscale, с. 4, авторы объясняют выбор локальной копии у потребителя. [DX12 shared heaps](https://learn.microsoft.com/en-us/windows/win32/direct3d12/shared-heaps) · [Синхронизация очередей DX12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/user-mode-heap-synchronization).

## Первый перенос

1. **Подключить адаптер.** Добавить явный выбор GPU для Cloud Picture в [SceneCloudPicture](../../Apps/App/src/Techniques/SceneCloudPicture.cpp). Штатная конфигурация продолжает генерировать облака локально. Для удалённой выбрать устройство по фактическому DXGI-адаптеру и сверить LUID. При невозможности открыть пару сообщить причину. Существующий `App.Async.CloudPicture` управляет локальной очередью.
2. **Запустить независимого производителя на GPU1.** Создать его [Executor](../../Apps/App/src/Graph/RenderGraphExecutor.h) в потоке, который будет вызывать `TryBegin`, `Reserve`, `Execute` и завершать работу. Оба executor используют один [QueueSubmission](../../Apps/App/src/Graph/QueueSubmission.h). У GPU1 свои PSO, дескрипторы, локальная UAV и слоты записи команд. Перед каждым dispatch фиксировать время и параметры того же шейдера. Вычисление и экспорт можно отправить по порядку на одной COMPUTE-очереди GPU1. После завершения экспорта производитель самостоятельно публикует результат и проверяет возможность следующего запуска. Для прогресса ему не нужен вызов `Draw` или `Present`.
3. **Передать изображение.** GPU1 пишет локальную UAV-текстуру и копирует её в ресурс общей кучи. GPU0 импортирует в свою sampleable-текстуру. Обе стороны открывают собственные D3D12-объекты для одной области памяти. Вариант с размещённым общим буфером использует `GetCopyableFootprints` и две `CopyTextureRegion`; шаг строки и объём брать из footprint. Это позволяет сохранить текущий формат и произвольные разрешённые размеры. Исторический пример такого переноса — `git show e8bba652:Apps/App/src/Techniques/CloudPictureTexture.cpp`. Активный маршрут был удалён в `8e291b95`.
4. **Подключить импорт к графу GPU0.** Выбранную локальную текстуру передать в существующий `PrepareMaterials` и инспектор. Объявить запись импорта и чтение той же текстуры в графе. Связать пакет импорта с выданным токеном именно выбранного экспорта через `PacketWait`. Опрос на CPU выбирает версию, межадаптерный fence упорядочивает доступ к её байтам на GPU. Геометрия без зависимости от облаков может выполняться раньше.
5. **Защитить три ресурса.** Локальную UAV GPU1 можно перезаписать после её экспорта. Общий слот можно перезаписать, когда он снят с публикации и GPU0 завершил все импорты из него. Локальная текстура GPU0 живёт до завершения её читателей. Перед заменой разрешения или устройств завершить работу со старыми ресурсами на обеих сторонах. При частичной ошибке учитывать уже отправленные пакеты.
6. **Принять один режим.** Release-сборка и один короткий обычный smoke на двух разных аппаратных адаптерах. На стене Bistro видны движущиеся облака, кадр выводится без явных ошибок. В конце прогона вывести оба LUID, число завершённых экспортов, число кадров с активной картиной после начального заполнения, число отправленных импортов и число повторных импортов той же версии. Счётчик импортов должен совпасть с числом таких кадров даже при повторах. Число повторов зависит от темпа карт. Один GPU подтверждает только локальный путь. Следующий вариант синхронизации — отдельное изменение после приёмки этого.

### Как выбрать целую версию, пока GPU1 пишет следующую

- Предлагаются три общих слота вне кольца кадров GPU0. Пока GPU0 дочитывает A, GPU1 может держать готовую B и писать C. Если GPU0 приостановлен, после публикации C производитель может снова использовать B, как только у B нет читателей. Двух слотов достаточно для перекрытия одной записи с одним чтением, но закреплённый за медленным потребителем слот тогда может остановить последующие обновления. Метаданные слота включают поколение ресурсов, номер обновления и токен экспорта.
- В начале подготовки кадра GPU0 выбирает наибольший завершённый номер в текущем поколении через `QueueSubmission::Complete`. На время выбора и до регистрации импорта закрепляет слот за кадром. Затем каждый кадр отправляет реальную copy-команду в свою локальную текстуру. Даже повторный импорт продлевает срок использования общей области. Граф связывает импорт с первым чтением на GPU0.
- Под общей короткой блокировкой производитель публикует завершённый слот, а потребитель выбирает и закрепляет его до регистрации токена импорта. GPU1 не перезаписывает текущую публикацию, а прежний слот получает обратно только после последней копии GPU0. Если свободных слотов нет, ждёт только поток производителя, с возможностью прерывания при остановке. На первом запуске предложено один раз связать импорт с реально выданным токеном первого экспорта через GPU fence. Далее кадр GPU0 никогда не ждёт вычисляемую версию. При выключении, смене устройства или размера прекратить выдачу новых работ, разбудить производителя, дождаться выхода и завершения отправленных работ обеих сторон до освобождения старого поколения.
- Например, в начале кадра 42 экспорт №17 готов, №18 ещё выполняется. GPU0 импортирует №17. В кадре 43 он снова импортирует №17, если №18 всё ещё занят. Когда №18 завершится, следующий выбор переключится на него. Готовность №18 и завершение чтения №17 — два разных события.

**Время анимации согласовано.** При старте удалённого пути зафиксировать текущую фазу времени Bistro и начало отсчёта монотонных часов. Для каждого dispatch брать базовое время плюс реально прошедшие секунды. Передавать его в `TotalTime` и применять `App.CloudPicture.SpeedScale` тем же способом, что и в локальном шейдерном пути. Настройки передавать потоку производителя согласованным снимком. Фаза продвигается между кадрами и за время занятости слотов. Более быстрая GPU1 выдаёт больше промежуточных изображений при той же скорости движения. Фиксированный шаг кадрового бенчмарка Bistro не определяет время удалённых облаков.

## Режимы Cloud Picture после третьего этапа

Настройка `App.CloudPicture.CrossSync` действует при выборе дополнительного адаптера через `App.CloudPicture.Adapter`. Значение по умолчанию — 0. Числа в INI и редакторе CVar используют таблицу ниже. Текстовые значения прежних INI сохраняют своё поведение: `true` означает 1, `false` означает 2. При смене режима или размера обе карты завершают работу старого поколения, затем история начинается заново.

| Режим | Кто запускает GPU1 | Какую версию импортирует GPU0 |
|---|---|---|
| 0 | Каждый кадр N ровно один раз, со временем и SpeedScale этого кадра | Ровно N−1. Первый кадр нового поколения импортирует свой экспорт. Кадры 1, 2, 3, 4 показывают 1, 1, 2, 3. |
| 1 | Каждый кадр N ровно один раз, со временем и SpeedScale этого кадра | Ровно N. |
| 2 | Независимый поток со временем от монотонных часов | Последнюю готовую целую версию, включая повторы. Первый импорт может ждать начального заполнения. |

В режимах 0 и 1 GPU1 запускает dispatch и копию в shared на COMPUTE после освобождения контекста записи. В режиме 0 кольцо общих слотов идёт по порядку заказов и имеет один дополнительный слот для истории. Предыдущий заказ хранит слот, номер и выданный токен. Повтор первой версии тоже регистрирует токен чтения. Общий слот можно перезаписать после ухода версии из истории и завершения всех её импортов. Локальная текстура GPU0 защищена кадровым слотом рендера.

GPU0 привязывает токен выбранного заказа через `PacketWait` только к пакету `cloud picture GPU0 import`. Перед копией очередь ждёт конкретное значение shared fence. Обычно это COPY, при `App.Async.Queues=0` — DIRECT. Независимые проходы могут идти раньше. Проход постера и инспектор читают локальную текстуру по зависимостям графа.

Приёмка третьего этапа — Release и один короткий обычный запуск Bistro на двух адаптерах с `CrossSync=0`. В журнале первых показов ожидаются пары «заказанная / импортированная версия» 1/1, 2/1, 3/2. После штатного выхода доступны суммарные экспорты, импорты, показы и повторы.

## Возможные следующие эксперименты

| Эксперимент | Изменение относительно режима 2 |
|---|---|
| Копирование только новой готовой версии | Пропускать повторный импорт и сохранять последнюю готовую локальную текстуру GPU0 при смене кадрового слота. |
| Попытка обновления из Draw | Предлагать GPU1 работу один раз за кадр и пропускать попытку при занятости. GPU0 по-прежнему каждый кадр копирует последнюю готовую версию. |
