# Bistro Debug: итоговый план оптимизации и оценка резервного FrameResource
Created: 2026-11-08

Основание: текущая ветка `codex/bistro-rendering`, HEAD перед этим документом
`4d9ba6d`; независимая проверка исходных оптимизаций и два последующих исследования.
Документ содержит анализ и порядок будущих работ. Он не внедряет новые расписания,
пулы, оптимизации, конфигурацию или ограничения качества.

**Цель:** не менее 20 реальных render FPS в Debug одновременно с физикой,
успевающей за игровым временем. Сохранить 60 Гц, TimeScale=1 для приёмки, CCD,
collision/solver steps, формы, counts, качество и импульсы. Не списывать accumulator,
не clamp входное время ради результата и не подменять Debug сборкой Release.

Сохраняются уже внедрённые snapshot/Settings/pose-signature caches, compact dynamic
shadows, root/command reuse, quaternion-to-Euler memoization и явно заданный Debug
linking. Не повторять их реализацию по старому плану 6 ноября. Не включать по
умолчанию ранее проигравшие rigid-shadow batching и water+particles async без
нового обоснования. Старый четырёхкадровый Nsight trace промежуточной сборки
показывал SPH ~17,54 мс, local shadows ~13,56 мс и sun shadows ~7,23 мс;
это ориентиры для нового профиля, не актуальная точная разбивка финального кода.

**Новая гипотеза: три рабочих слота плюс четвёртый резервный.**

Идея соответствует ограниченному пулу буферов с переиспользованием после fence
(fence-based resource reuse). Простой ring buffer — частный случай с фиксированным
порядком. Произвольная перестановка `1–2–3 → 4–2–3` не делает занятый слот свободным.

| Событие | Слот 1 | Слоты 2,3 | Слот 4 |
|---|---|---|---|
| Начало подготовки кадра 4 | GPU использует, fence не завершён | GPU использует | Свободен |
| Для кадра 4 выбран резерв | Всё ещё занят GPU | Всё ещё заняты | CPU готовит данные |
| Кадр 4 подготовлен, старый fence ещё не завершён | Всё ещё занят | Заняты | Подготовлен, либо уже отправлен GPU |
| Следующий кадр до освобождения любого fence | Нельзя взять | Нельзя взять | Нельзя взять: четыре комплекта исчерпаны |
| Fence слота 1 завершился | Теперь действительно свободен | По своим fences | По своему состоянию |

На одной очереди с возрастающими frame-retirement fences, если самый старый
слот ещё не завершён, более поздние fences тоже не завершены. Резерв полезен,
если за время подготовки в нём GPU успевает освободить старый слот. При длительном
отставании GPU дополнительные комплекты только отодвигают исчерпание пула;
длительность GPU-работы и устойчивая пропускная способность не меняются автоматически.
Для нескольких очередей/устройств освобождение должно покрывать всех пользователей,
либо опираться на доказанный join в итоговый retirement fence.

Не нужны ручные перестановки логического кольца. Корректная будущая модель:

```text
Free → CPU-owned → Ready → Submitted → Free только после retirement fence
```

Pool capacity, разрешённое число отправленных кадров, число backbuffers и число
CPU snapshots — разные ограничения. Слот 1 после вытеснения находится среди
ожидающих освобождения, а не в списке Free. Если свободных нет, симуляция может
продолжаться по своим срокам; создавать новые комплекты без предела нельзя.

Предпочтительная форма возможного опыта — до четырёх физических контекстов,
ограниченная отдельно очередь отправленных кадров и максимум один готовящийся
CPU-пакет. Если отправлять четвёртый GPU-кадр сверх прежней глубины очереди,
возраст изображения и input latency могут вырасти. Если глубину не увеличивать,
резерв может перекрыть подготовкой часть ожидания, но submit всё равно подчиняется
render admission. Это не гарантия повышения FPS.

Такое управление памятью соответствует
[Microsoft: Fence-Based Resource Management](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management).
Глубина очереди представления регулируется отдельно от наличия памяти; у DXGI есть
[отдельный механизм максимальной задержки swapchain](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_3/nf-dxgi1_3-idxgiswapchain2-setmaximumframelatency).
Наличие этого интерфейса не означает, что его можно включить без проверки используемых
presentation/FG wrappers и соответствующего swapchain flag.

**Что в нынешнем коде нельзя забыть при таком опыте.**

- `Apps/App.Base/src/RenderModule.cpp:897`: выбор слота сейчас modulo `Render.NumFrames`.
  Перестановка станет явным выделением/освобождением контекста, не заменой одной проверки.
- `Apps/App.Base/Include/App.Base/Systems/GPUDataUpdateSystem.h:35,62,120` и
  `Engine/Engine.RendererDX12/src/GDX12DeviceResources.cpp:181`: dirty counters
  предполагают регулярный обход слотов. Пример: material изменился один раз,
  три записи ушли в 4,2,3, счётчик закончился; позднее используемый слот 1 сохранил
  старый material. Для произвольного reuse нужны версии данных по слотам или
  доказанно полная актуализация выбранного слота. Увеличения одного счётчика мало.
- `Engine/Engine.RendererDX12/Include/Engine.RendererDX12/GDX12GPUTimer.h:40`:
  у query/readback ring фиксировано три позиции; `Start` способен ждать свой fence.
  Ожидание может переехать сюда даже после добавления FrameResource.
- `RenderModule.cpp:127`, `Engine/Engine.UI/src/UI_test.cpp:166`,
  `External/External.Libraries/imgui/src/backends/imgui_impl_dx12.cpp:315`:
  ImGui DX12 имеет собственный циклический набор buffers. Его безопасность должна
  сохраняться: четвёртый контекст движка не защищает автоматически третий UI ring.
- `Apps/App.Base/src/RenderModuleSkinning.cpp:234,438`: число кадров и slot index
  используются skinning meshes/palettes. Это тоже часть аудита ресурсов.
- `RenderModule.cpp:1252`: обычный swapchain создаётся с **двумя backbuffers**,
  независимо от трёх FrameConstants. Добавление контекста не отменяет pacing/Present.
- `GDX12RenderGraph.cpp:424,553,569`: бывают промежуточные submits. Нельзя ждать
  только перед последним submit, уже записав или отправив работу с занятыми данными.
- `Engine/Engine.RendererDX12/src/GDX12Resource.cpp:91`: tracked resource state
  изменяется при получении barrier во время записи. Нельзя без отката выбрасывать
  уже записанные command lists ради «ещё более нового» состояния. Latest-state
  replacement относится прежде всего к CPU snapshot до материализации GPU-команд.

Дополнительный контекст занимает ещё один набор кадровых buffers и связанных
ресурсов; точный объём RAM/VRAM не измерен. Это не обязательно копия всех текстур
Bistro, но и не бесплатное переименование указателя.

**Вердикт для текущей ситуации.** В последнем trace условие входа в резерв не
возникло ни разу из 1800 measured frames. Поэтому нет оснований делать четвёртый
слот первым исправлением нынешнего долга или обещать от него FPS. Пул может
помочь редким задержкам/вариативности CPU/GPU и пригодиться будущей архитектуре.
Его включение должно зависеть от нового профиля, где именно нехватка контекста
видна на критическом пути, а не от одного факта «GPU ещё работает».

Если такой профиль появится, первым дешёвым контролем должен быть обычный
последовательный ring из четырёх: существующий стартовый `Render.NumFrames`
уже допускает значение 4. Проверить его в изолированном опыте без постоянной
правки INI, с учётом query ring и input latency, проще, чем сразу писать
динамический pool. Это ещё не реализация условного резерва 3+1. К адаптивному
выбору переходить только при доказанной пользе и необходимости такой политики.

Номера этапов задают приоритет, а не обязанность реализовать всё. После каждого
изменения проверять полный целевой результат. Если он устойчиво достигнут,
остановиться: не строить потоковую архитектуру или новый pool ради самого наличия.
При архитектурной необходимости этапы 4–5 можно проектировать после этапа 1,
но их выигрыш всё равно нужно сравнивать с меньшими изменениями. GPU-часть этапа 3
нужна независимо, если на целевом прогретом устройстве GPU выходит за 50 мс.

Для CPU capacity последнего профиля средняя условная оценка — ~374 мс/с на
60 тиков плюс ~32,6 мс остальной работы на render iteration. При 20 FPS это
~1026 мс работы одного управляющего потока за секунду даже без Present.
Это не прогноз новой архитектуры, но объясняет отсутствие бесплатного CPU-резерва.
Увеличение числа слотов не уменьшает ни одно из этих слагаемых.

**Как объединить все пользовательские гипотезы.** Независимую CPU-подготовку
вынести до ожидания там, где измерено ожидание и данные действительно независимы.
Вычислять каждый положенный physics tick независимо от принятия изображения.
Ресурсы выбирать по готовности fence, а не запрещать работу только потому, что
GPU занят. При этом не ждать полной пустоты GPU и не раздувать очередь старых
снимков. Резервный контекст допустим как ограниченная память для подготовки,
а не как замена политике latency/admission.

У Jolt и GPU-техник остаются разные бюджеты. Вода сейчас симулируется в render
graph и ограничивает elapsed через safeStep*MaxSubsteps; пропуск изображения
не гарантирует сохранение всей эволюции SPH. Частицы/трава, временные эффекты,
camera/bones и motion vectors должны получать согласованный интервал между
своими реальными обновлениями. Нельзя просто вызвать старый Update N раз без Render.

**Критерии готовности и ограничения доказательств.**

- `Aend = Astart + requested − completed_ticks*h` сходится; накопленное время не
  обрезается. После пиков долг погашается, на одинаковых фазах последующих волн не растёт.
- FPS, physics tick jitter, p95, очередь/возраст snapshot на capture/submit/present,
  расход памяти и GPU thermal/power reasons записываются вместе.
- Для 3+1 отдельно сравниваются случаи неизменной глубины GPU queue и разрешённого
  дополнительного submitted frame. Уменьшение CPU wait при увеличенной задержке
  не объявляется безусловной оптимизацией.
- Проходят соответствующие изменению тесты, D3D12 debug layer и depth/HDR проверки;
  проверены resize/minimize, pause/TimeScale, creation/removal и sleep/wake.
- Уже измеренные локальные выгоды не обещают суммарного FPS; независимость потоков
  не означает независимость CPU/GPU питания/памяти ноутбука. Температура и эффективные
  частоты CPU пока не получены, причинных утверждений о CPU throttling нет.
- Новый 3+1 pool, отдельный renderer thread и их A/B в этой задаче не реализованы.
  Новые тяжёлые замеры не запускались: проверка опирается на актуальный код и уже
  сохранённый trace; runtime-выигрыш изменённой архитектуры остаётся проверкой реализации.
