# Поэтапный перенос Bistro в MetaRenderGraph

## Согласовано 2026-11-15

Переносить техники по одной. После каждого завершённого шага пользователь проверяет FPS и нагрузку CPU/GPU; следующий шаг начинается только после его решения. Итоговое сравнение архитектуры и производительности App и App.MetaRenderGraph проводится после завершения переноса.

## Этап 1: статический Opaque

- Исходные интерьер и экстерьер Bistro, без размножения физических предметов и добавлений бенчмарка.
- Существующие материалы и текстуры App, GPU culling, depth prepass, GBuffer, PBR, исходные светильники и статический SkyBox/IBL, вывод HDR на экран.
- Только непрозрачный путь (включая существующие вырезы по маске в OpaquePass). Полупрозрачные материалы не рисуются; отдельного transparency/composition прохода нет.
- Без теней, AO, SSR, локальных reflection probes, облаков, травы, воды, частиц, анимации, физической симуляции, постэффектов, реконструкции и генерации кадров.
- Обычный запуск App.MetaRenderGraph открывает этот этап. Исходный диагностический fixture остаётся отдельным режимом --smoke, не используется для приёмки этапа.
- Начальная камера соответствует App: у входа, с возможностью свободного перемещения. Native resolution, один основной GPU, существующее размещение Meta packets на очередях.

## Проверка и передача

Release-сборка и один короткий обычный smoke: запуск, GPU-работа, видимый результат, отсутствие явных ошибок. Без дополнительных тестовых матриц, сравнений точности и профилирования. После smoke передать пользователю исполняемый файл и коммит; к следующей технике не переходить.

### World-space canvas и облака-картина

World-space UI — реальные поверхности в мире с перспективой, окклюзией геометрией
и offscreen UI в материале; экранный HUD остаётся отдельным output-sized проходом.
Переиспользовать `BistroUICanvases.h`, `Rendering/UI/BistroUIPosters.*`, Engine.UI
и диагностический `ScenePostUI::AppendPosters`. В ordinary конструктор ScenePostUI
сейчас пропускает posters; одной настройки screen UI недостаточно. Подготовка
материалов идёт после ожидания frame slot, до uploads; producer → material reads
объявляются только фактическим потребителям, без зависимости всех DIRECT packets.
Содержимое и эффекты сверить с `D:\Project\Multi-GPU-Render-DX12\MGPU-IMGUI`
(`README.md`, `HybridUIApp.cpp`, `UILayer.*`, `UIQuality.h`). Там уже есть offscreen
UI, presets и single/mGPU transfer; размещение в Bistro брать из BistroUIPosters.
Не переносить benchmark loop/ExitProcess sample. Сохранить анимацию canvas при
paused сцене и явно задокументировать canvas resolution/quality controls.

Картина облаков — отдельная анимированная процедурная текстура из
`D:\Project\Multi-GPU-Render-DX12\MGPU-Noise\Shaders\CloudsNoiseCS.hlsl`
и `Common/CloudGenerator.*`, отображаемая на стене. Источник уточнён пользователем:
перенести именно MGPU-Noise, а не cubemap-алгоритм GDX12CloudComponent из PEPEngine2. Она не
подменяет global sky/IBL и не запускает облака одновременно поверх всей сцены.
Разрешение текстуры (width/height) независимо от окна, SR, размеров картины и UI
canvas; GPU вычисления выбирается явно через CVar/INI. Использовать существующие
настройки, новые вводить только для отсутствующих controls. Записать requested и
effective resolution/adapter; недоступный адаптер не скрывать молчаливой подменой.
Primary GPU читает локальную текстуру напрямую; для другого GPU использовать
существующий Meta transport с publication/fences и безопасным повторным
использованием слотов. Не передавать текстуру через CPU readback/upload и не
пересоздавать её каждый кадр. Зафиксировать политику свежести и возможную задержку
в кадрах; разрешение и adapter меняются с retirement старых ресурсов/descriptors.
Облака и UI имеют отдельные producers и controls; общий только способ показа
текстуры в мире. Существующий Meta.SceneEnvironment::SetClouds выбирает clouds
как источник environment — для картины этот путь напрямую не подходит.

В этапе реконструкции переиспользуются существующие провайдеры Native, XeSS,
FSR, DLSS и NIS и поддерживаемые ими presets. Native — passthrough без
самостоятельного TAA. Native-resolution temporal AA предоставляют XeSS AA,
FSR NativeAA и DLSS DLAA; NIS выполняет пространственное масштабирование.
Разработка собственного TAA этим планом не запрашивается. Наличие provider
в App не означает, что его обычный Meta-путь уже перенесён или проверен;
фактическая доступность SDK/адаптера определяется при соответствующем этапе.
